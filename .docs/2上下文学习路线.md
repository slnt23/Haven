# Haven Context 系统 — 作者学习路线

> 目标：独立讲清楚 Context Engineering 的工程实践，区分 RAG 与 Agent Context 的本质差异。
> 读者定位：开发者（非 AI 研究员），重点讲工程实现。

---

## 1. 先纠正一个常见误解

### RAG ≠ 往 prompt 里塞文档

大多数开发者理解的 RAG：

```
用户问 → embedding 检索 → 把文档片段拼到 prompt 里 → LLM 回答
```

这不是 RAG，这只是 **检索增强**。真正的 RAG (Lewis et al., 2020) 有严格的学术定义：端到端联合训练 retriever + generator。工程实践中，99% 的"RAG"其实是 **In-Context Retrieval**。

Haven 的 ContextManager 做的是更基础也更重要的东西：**Context Engineering**。

---

## 2. 什么是 Context Engineering

**定义：在单次 LLM 调用前，从多个来源收集、排序、裁剪信息，组装成最优的 system prompt。**

与 Prompt Engineering 的区别：

| | Prompt Engineering | Context Engineering |
|---|---|---|
| **操作对象** | 指令文本 | 信息集合 |
| **关注点** | 措辞、角色设定、few-shot | 信息优先级、token 预算、来源可信度 |
| **变化频率** | 低 (改一次用很久) | 高 (每次调用的上下文都不同) |
| **瓶颈** | 措辞精度 | token 窗口容量 |

**为什么 Context 比 Prompt 更重要？**

一个例子：

```
Prompt A (没有 Memory):
  "你是一个 AI 助手，请回答用户问题。"

Prompt B (有 Memory):
  "你是一个 AI 助手。
   [用户信息] 姓名: 张三, 过敏: 猫, 职业: 后端工程师
   [相关历史] 上周讨论过 Python 异步编程
   请回答用户问题。"
```

Prompt A 和 B 的指令部分完全相同。但 B 的回复质量远超 A —— **不是因为 Prompt 写得更好，而是因为 Context 更丰富。**

## 3. 当前项目中的上下文架构

### 3.1 整体架构

```
用户输入 → AgentRuntime.run()
              │
              ├─ 1. ContextManager.build(**sources)
              │      │
              │      ├─ collect()  ← 从 6 个来源收集 ContextItem
              │      │    ├─ _collect_skills(personality_skills)    → PERSONALITY
              │      │    ├─ _collect_skills(domain_skills)         → SKILL
              │      │    ├─ _collect_memory()                     → MEMORY
              │      │    ├─ _collect_workflow(workflow_state)      → WORKFLOW
              │      │    ├─ _collect_tool_results(tool_results)    → TOOL_RESULT
              │      │    ├─ _collect_rag(rag_context)             → RAG
              │      │    └─ extra_collectors (插件扩展)
              │      │
              │      └─ assemble(items)
              │           └─ ContextAssembler.assemble(items)
              │                ├─ 按 priority 升序排列 (0 = 最高)
              │                ├─ TokenBudget.estimate() 逐个检查
              │                └─ 超出时截断 + 标记 "[已截断]"
              │
              ├─ 2. PromptBuilder.build(bundle)
              │      └─ 最终 token 预算校验 (安全网)
              │
              └─ 3. build_messages(task, system_prompt)
                     └─ [SystemMessage, ...History, HumanMessage(task)]
```

### 3.2 核心类型

#### ContextItem — 上下文原子单元

```python
@dataclass
class ContextItem:
    content: str                        # 文本内容
    source: ContextSource               # 来源枚举
    priority: int                       # 优先级 (0=最高)
    metadata: dict[str, Any]            # 附加元数据 (skill_name, confidence...)
```

每条 ContextItem 携带三个关键属性：
- **来源** (source) — 决定可信度和用途
- **优先级** (priority) — 决定在 token 预算紧张时谁先被裁
- **元数据** (metadata) — 调试和过滤用，不注入 prompt

#### ContextSource — 六类来源

```python
class ContextSource(Enum):
    PERSONALITY = "personality"    # 优先级 0 — 人格 skill (haven.md)
    SKILL = "skill"                # 优先级 1 — 领域 skill (coder, medical...)
    MEMORY = "memory"              # 优先级 2 — 长期记忆 (Semantic facts)
    WORKFLOW = "workflow"          # 优先级 3 — 工作流状态 (当前节点+输出)
    TOOL_RESULT = "tool_result"    # 优先级 4 — 工具执行结果
    RAG = "rag"                    # 优先级 5 — 外部知识检索
```

#### ContextBundle — 组装结果

```python
@dataclass
class ContextBundle:
    system_prompt: str              # 最终组装好的 prompt 字符串
    items: list[ContextItem]        # 本次收集的所有 item (调试用)
    token_usage: int                # 估算的 token 用量
```

#### ContextAssembler — 组装引擎

```python
class ContextAssembler:
    def assemble(self, items: list[ContextItem]) -> str:
        sorted_items = sorted(items, key=lambda x: x.priority)
        # 逐个检查 token 预算，超出的截断或丢弃
```

#### TokenBudget — Token 估算器

```python
class TokenBudget:
    def estimate(self, text: str) -> int:
        chinese_chars = sum(1 for c in text if "一" <= c <= "鿿")
        other_chars = len(text) - chinese_chars
        return int(chinese_chars * 1.5 + other_chars / 3)
```

#### ContextManager — 统一入口

```python
class ContextManager:
    def build(**kwargs) -> ContextBundle:    # 一站式: collect + assemble
    def collect(**kwargs) -> list[ContextItem]:  # 仅收集
    def assemble(items) -> str:              # 仅组装

```

## 4. 与传统 RAG 的区别

### 4.1 传统 RAG 流水线

```
用户问题 → Embedding 检索 → Top-K 文档 → Prompt 模板拼接 → LLM 生成
```

问题：
- **只有一个来源** (知识库)，Agent 运行时有 6+ 个来源
- **没有优先级**，所有文档平等对待
- **没有来源标记**，LLM 分不清哪段是用户信息、哪段是外部文档

### 4.2 Haven ContextManager 的做法

```
用户问题 → 6 个来源并行收集
          → 每条 item 标注 source + priority
          → TokenBudget 从低优先开始裁剪
          → 按 source 分组标记，LLM 一眼可辨
```

核心差异：

| | 传统 RAG | Haven ContextManager |
|---|---|---|
| **来源数** | 1 (知识库) | 6 (人格/技能/记忆/工作流/工具/RAG) |
| **优先级** | 无 | 0-5 六级 |
| **来源标记** | 无 | 每条带 source 元数据 |
| **Token 管理** | 硬截断 | TokenBudget 分级裁剪 |
| **扩展性** | 硬编码 | register_collector() 插件 |

### 4.3 为什么很多 Agent 不是真正的 RAG

"Agent RAG" 这个说法在工程界被严重滥用了。很多项目做的实际上是：

```
把 memory 查询结果拼到 prompt 里 → 自称 RAG
把工具输出拼到 prompt 里 → 自称 RAG
把 skill prompt 拼到 prompt 里 → 自称 RAG
```

正确的分类：

- **检索增强 (Retrieval Augmentation):** 把检索到的信息拼到 prompt 里 — 这是语境注入，不等于 RAG
- **真正的 RAG:** retriever + generator 端到端训练，梯度从 generator 回传到 retriever

Haven 的 ContextManager 做的就是 **检索增强的工程化实现** — 但来源不是"文档库"，而是 **6 个异构上下文源**。

面试时这样讲：
> "我们不是一个简单的 RAG 系统。ContextManager 做的是多源上下文编排——Memory 提供用户画像、Skill 提供领域指令、Workflow 提供任务状态、Tool 提供执行结果。RAG 只是其中一个来源，优先级排在最后。"

## 5. Token Budget 如何工作

### 5.1 为什么需要 Token Budget

LLM 的上下文窗口有限。即使 Claude 支持 200K tokens，往 system prompt 里无脑塞内容仍然有问题：
- 注意力稀释 — 内容越多，LLM 对每条信息的关注度越低
- 成本线性增长 — 输入 token 按量计费
- 推理质量下降 — "大海捞针"效应

### 5.2 Haven 的实现

```python
class TokenBudget:
    def estimate(self, text: str) -> int:
        chinese_chars = sum(1 for c in text if "一" <= c <= "鿿")
        other_chars = len(text) - chinese_chars
        return int(chinese_chars * 1.5 + other_chars / 3)
```

**为什么不用 tiktoken？**

tiktoken 精确但会引入额外依赖。对于 system prompt 级别的 token 估算，1% 的误差无关紧要——因为最终的硬截断安全网在 `PromptBuilder.build()` 中会用 3 chars/token 再截一次。

**中文补偿：** 中文字符占 1.5 token/char，CJK 范围 `一-鿿`。这是工程经验值，不是规范值。

### 5.3 裁剪策略

```python
# ContextAssembler.assemble()
for item in sorted_items:          # 按 priority 升序
    if used + est <= max_tokens:
        parts.append(content)      # 放得下 → 完整放入
        used += est
    else:
        if remaining > 100:        # 剩余空间还够 → 截断
            truncated = content[:remaining * 3] + "\n...[已截断]"
            parts.append(truncated)
        break                      # 剩余空间不够 → 丢弃 + 停止
```

关键点：
- **`remaining > 100` 这个阈值**：小于 100 tokens 的剩余空间不值得截断（会截出碎片），直接丢弃
- **break 而非 continue**：按优先级排列后，第一个放不下的 item 之后的更低优先级 item 也一律丢弃。这是保证优先级语义的关键

## 6. Context 排序策略

### 6.1 优先级设计原理

```
PERSONALITY  = 0  "你是谁" → 最高优，不可裁剪
SKILL        = 1  "你擅长什么" → 次高优
MEMORY       = 2  "关于用户的已知信息" → 中优
WORKFLOW     = 3  "当前任务进度" → 中低优
TOOL_RESULT  = 4  "上一步工具输出" → 低优 (LLM 可能已经知道)
RAG          = 5  "外部参考资料" → 最低优 (仅当有空间时附带)
```

设计逻辑：
1. **人格和技能定义了 Agent 的身份边界**，没了它们 Agent 就不再是 "Haven" — 最高优
2. **Memory 是对话质量的保证**，比工作流状态更重要 — 中优
3. **RAG 是锦上添花**，没有也能正常工作 — 最低优

### 6.2 裁剪顺序

当 token 预算不够时，从后往前裁：

```
优先保留                          优先丢弃
  PERSONALITY → SKILL → MEMORY → WORKFLOW → TOOL_RESULT → RAG
```

一个典型场景 (4000 token budget)：

```
假设 6 段上下文共 6000 tokens:
  RAG (1500)      → 丢弃 (超出预算且优先级最低)
  TOOL_RESULT (500) → 截断为 200
  WORKFLOW (1200)   → 完整保留
  MEMORY (800)      → 完整保留
  SKILL (1500)      → 完整保留
  PERSONALITY (500) → 完整保留 (最高优)
  总计: 4200 → PromptBuilder 再硬截到 4000
```

## 7. ContextManager 数据流详解

### 7.1 一次完整的 build() 调用

```python
cm = ContextManager(memory=runtime.memory)

bundle = cm.build(
    personality_skills=[haven_skill],       # haven.md 人格
    domain_skills=[coder_skill],            # Planner 选择的 coder skill
    use_memory=True,                         # 查询 SemanticMemory
    workflow_state=workflow_state,           # 当前节点 + 输出
    tool_results={"web_search": "..."},      # 上一步工具结果
    rag_context="[外部检索到的文档...]",       # RAG 检索结果
)
```

### 7.2 各来源的收集逻辑

#### PERSONALITY (collected from Skill.prompt)

```python
# haven.md → BaseSkill(name="haven", prompt="你是 Haven, 一个 AI 助手...", default=True)
@staticmethod
def _collect_skills(skills, source):
    for skill in skills:
        prompt = skill.prompt_extension or skill.prompt
        if prompt.strip():
            items.append(ContextItem(content=prompt, source=source))
```

**注意：** 人格 skill 的 `default=True` 属性由 `SkillRegistry.get_defaults()` 识别，但注入时与其他 skill 无异 — 唯一的区别是 **priority=0 vs priority=1**。

#### SKILL (collected from Skill.prompt)

与 PERSONALITY 相同的收集逻辑，但 priority=1。PlannerAgent 的选择结果直接映射到此处。

#### MEMORY (collected from AgentMemory facade)

```python
def _collect_memory(self):
    ctx = self._memory.get_long_term_context()
    # 返回格式:
    # "[长期记忆 — 以下是你已知的关于当前用户的信息]
    #  - name: 张三
    #  - allergy: 猫
    #  - primary_lang: Python"
```

**关键限制：** 最多 15 条事实，confidence ≥ 0.3。这保证了 Memory 注入不会爆炸。

#### WORKFLOW (collected from WorkflowState)

```python
@staticmethod
def _collect_workflow(state):
    # 1. 当前节点名 → "[当前工作流阶段: coder]"
    # 2. 每个节点的输出 → 截断 600 字符
```

为什么要截断 600 字符？一个 workflow 可能有 5 个节点，每个节点输出可能几千字。全部注入会撑爆 token 预算。

#### TOOL_RESULT (collected from dict)

```python
@staticmethod
def _collect_tool_results(results: dict[str, str]):
    for tool_name, result in results.items():
        items.append(ContextItem(
            content=f"[工具 '{tool_name}' 执行结果]\n{result[:800]}",
            source=ContextSource.TOOL_RESULT,
        ))
```

**截断 800 字符** — 工具结果可能很长（网页搜索返回几千字），但 LLM 只需要知道 "搜索到了什么关键信息"，不需要原文全文。

#### RAG (collected from raw string)

```python
@staticmethod
def _collect_rag(rag_context):
    if not rag_context.strip():
        return []
    if not context.startswith("["):
        content = "[参考知识 — 请优先基于以下资料回答]\n" + content
    return [ContextItem(content=content, source=ContextSource.RAG)]
```

**自动加前缀** — 如果外部传入的 RAG 内容没有自己的标签，自动标注来源。这让 LLM 知道自己正在参考外部资料而非内部记忆。

### 7.3 插件扩展

```python
cm.register_collector(
    ContextSource.TOOL_RESULT,
    lambda: ContextItem(content="自定义上下文", source=ContextSource.TOOL_RESULT)
)
```

扩展点在 `collect()` 的最后一步执行。任何实现了 `() → ContextItem | list[ContextItem]` 签名的 callable 都可以注册。

## 8. 面试常见问题

### Q1: ContextManager 和 PromptBuilder 的分工是什么？

**答：** ContextManager 负责"收集什么" (what)，PromptBuilder 负责"怎么组装" (how)。

具体来说：
- ContextManager: 从 6 个来源收集 ContextItem，按优先级排序，token 预算裁剪 → 输出 ContextBundle
- PromptBuilder: 接收 ContextBundle，做最终 token 校验（安全网），添加系统级包装 → 输出 system prompt 字符串

为什么拆成两个？**单一职责。** ContextManager 不需要知道 prompt 的格式细节，PromptBuilder 不需要知道数据从哪来。换一个 PromptBuilder 实现（比如 JSON 格式输出）不影响 ContextManager。

### Q2: 为什么 RAG 的优先级最低？

**答：** 因为"没了 RAG Agent 还能工作，没了人格 prompt Agent 就不是 Agent 了"。

优先级反映的是信息对 Agent 身份和能力的**必要性**，不是信息的**质量**。RAG 查询到的文档可能非常高质量，但它不是 Agent 行为的核心驱动因素。

工程证据：把 RAG 优先级设为 0（最高）→ token 预算紧张时 RAG 挤掉 MEMORY → LLM 知道外部文档但不知道用户是谁 → 回复质量反而下降。

### Q3: TokenBudget 用估算而不是精确计数，为什么？

**答：** 三个原因：

1. **性能** — tiktoken 的精确计数需要在 Python 中遍历 token 序列。对 < 4000 tokens 的 system prompt，误差 < 20 tokens，不值得引入额外依赖。
2. **安全网** — PromptBuilder 最后会用 3 chars/token 硬截断一次，即使估算偏小也不会有实际溢出。
3. **中文补偿** — 1.5x 系数覆盖了 CJK 的编码膨胀，比默认的 chars/4 估算更准确。

### Q4: 截断 `remaining > 100` 这个魔数怎么来的？

**答：** 工程经验值。

- 100 tokens ≈ 300 字符 ≈ 一句半中文。少于这个长度的截断没有意义 — 用户看到"[已截断]"标记后面的半句话比看不到更困惑。
- 实际上这个阈值是可调的（construction parameter），100 是针对中文对话场景的默认值。

### Q5: ContextManager 是可插拔的吗？

**答：** 是。通过三个层面：

1. **来源可插拔** — `register_collector()` 注册自定义来源
2. **组装可替换** — `assemble()` 方法是公开的，可以在 `collect()` 和 `assemble()` 之间插入自定义逻辑
3. **实现可替换** — AgentRuntime 持有 `context_manager` 引用，传入不同的 ContextManager 子类即可

### Q6: 如何调试 Context 注入？

**答：** `ContextBundle.items` 保留了本次收集的所有 item，包含来源和优先级。

调试技巧：
```python
bundle = cm.build(...)
for item in bundle.items:
    print(f"[{item.source.value}] p={item.priority} len={len(item.content)}")
```

从输出了解哪些来源被完全保留、哪些被截断、哪些被丢弃。
