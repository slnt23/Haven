# Haven Runtime 系统 — 作者学习路线

> 目标：以 Agent Framework 作者视角，独立讲清楚 Agent Runtime 的架构设计。
> 读者定位：框架开发者，重点讲架构决策和工程取舍。

---

## 1. Agent Runtime 到底是什么

### 1.1 一句话定义

**Agent Runtime = LLM 调用 + 工具执行 + 消息管理 + 上下文组装 + 状态追踪。**

不是训练框架，不是推理引擎，不是 prompt 模板。Runtime 是一个**编排层**——它不"做"具体的事，它负责调度 LLM、工具、记忆、上下文在正确的时机以正确的顺序协作。

### 1.2 类比：操作系统内核

```
操作系统内核          Agent Runtime
─────────────        ──────────────
进程调度       ←→    LLM 调用 + Tool 调用循环
内存管理       ←→    WorkingMemory + SemanticMemory
文件系统       ←→    EpisodicMemory (持久化)
中断处理       ←→    retry_async (错误恢复)
系统调用       ←→    ToolResolver (工具匹配)
上下文切换     ←→    ContextManager (上下文组装)
```

### 1.3 Haven Runtime 的职责边界

```python
# 职责范围（仅 5 项）:
#   1. LLM     — 模型初始化、切换、bind_tools
#   2. Tool    — 工具注册/绑定/执行调度
#   3. Memory  — 短期消息窗口 + 长期事实存储
#   4. State   — 会话状态
#   5. Context — 上下文收集与组装（委托 ContextManager）

# 明确排除:
#   - 不分类用户意图          → PlannerAgent
#   - 不决定激活哪些 skill     → PlannerAgent
#   - 不含任何硬编码人格 prompt → Skills
#   - 不直接读取子系统         → ContextManager
```

这个边界是 Haven 与大多数 Agent 框架最核心的差异——**Runtime 不做决策，只做执行。**

## 2. Planner 与 Runtime 分离的意义

### 2.1 大多数 Agent 框架的做法

```
class Agent:
    def run(self, task):
        # 在同一个方法里做规划 + 执行
        intent = self.classify(task)       # 分类
        skills = self.select_skills(task)  # 选择
        prompt = self.build_prompt(...)    # 组装
        response = self.llm.ainvoke(...)   # 执行
        return response
```

问题：**规划逻辑和执

行逻辑耦合。** 改规划可能影响执行，测执行需要 mock 规划。

### 2.2 Haven 的做法

```python
# planner.py — 规划层
class PlannerAgent:
    async def plan(self, task) -> ExecutionPlan:
        # 一次 LLM 调用 → structured output
        # 输出: {goal, intent, skills, steps, workflow}

# runtime.py — 执行层
class AgentRuntime:
    async def run(self, task, ...) -> str:
        # 不关心"为什么执行这个任务"
        # 只关心"怎么正确执行"

# 装配
planner = PlannerAgent(runtime)
result = await planner.execute(task)
```

### 2.3 分离带来的三个实际好处

**1. 测试隔离**

```python
# 测 Planner — mock Runtime
plan = await planner.plan("写代码")
assert plan.skills == ["coder"]

# 测 Runtime — 不需要 Planner
result = await runtime.run("hello", system_prompt="你是助手")
assert result == "预期输出"
```

**2. 路径可替换**

```python
# 生产环境: PlannerAgent → 完整的 3 路分发
result = await planner.execute(task)

# 简单场景: 跳过 Planner，Runtime 直通
result = await runtime.run(task)

# 批量任务: 自定义 Planner
class BatchPlanner:
    async def plan(self, tasks):
        return [await self._plan_one(t) for t in tasks]
```

**3. 关注点分离**

| 层 | 关心的输入 | 关心的输出 | 不关心 |
|---|-----------|-----------|--------|
| Planner | 用户意图 | skill 列表 + 步骤 | 工具怎么执行 |
| Runtime | system_prompt + tools | LLM 响应文本 | 为什么选这些 skill |

## 3. 一次用户请求完整生命周期

```
用户输入: "帮我写一个 Python 排序算法，要测试通过"
─────────────────────────────────────────────────────

Phase 1: 规划 (PlannerAgent.plan)
─────────────────────────────────────────────────────
  │
  ├─ _is_trivial("帮我写一个...") → False
  │
  ├─ _llm_plan(task)
  │    ├─ SkillRegistry.get_selection_context()
  │    │   → "coder: 代码编写, code_review: 代码审查, ..."
  │    ├─ llm.with_structured_output(ExecutionPlan)
  │    │   → 一次 LLM 调用，结构化输出
  │    └─ ExecutionPlan {
  │         goal: "编写并测试 Python 排序算法",
  │         intent: "development",
  │         complexity: "medium",
  │         skills: ["coder"],
  │         workflow: null,
  │         steps: [
  │           {order:1, desc:"需求分析", skill:"coder"},
  │           {order:2, desc:"编写代码", skill:"coder", depends_on:[1]},
  │           {order:3, desc:"测试验证", skill:"coder", depends_on:[2]}
  │         ]
  │       }
  │
  ├─ SkillRegistry.resolve_dependencies(["coder"])
  │    → ["coder"] (coder 无依赖)
  │
  └─ _validate_plan(plan)
       → skill "coder" 存在于 SkillRegistry → 通过

Phase 2: 执行 (PlannerAgent._execute_steps)
─────────────────────────────────────────────────────
  │
  ├─ _topological_sort(steps) → [step1, step2, step3]
  │
  ├─ Step 1: "需求分析"
  │    ├─ runtime.resolve_tools(["coder"])
  │    │    └─ ToolResolver.resolve(["coder"])
  │    │         → [code_exec, file_ops, web_search]
  │    ├─ context_manager.build(personality=[haven], domain=[coder])
  │    │    → ContextBundle {system_prompt: "你是 Haven... 你是代码专家..."}
  │    ├─ build_messages("需求分析", system_prompt)
  │    │    → [SystemMessage, History, HumanMessage("需求分析")]
  │    ├─ llm.ainvoke(messages) → response (无 tool_calls)
  │    └─ step_outputs[1] = "需求: 实现快速排序..."
  │
  ├─ Step 2: "编写代码"  (depends_on=[1])
  │    ├─ tool_results = {"step_1": step_outputs[1]}
  │    ├─ context_manager.build(..., tool_results=tool_results)
  │    │    → system_prompt 包含前一步结果
  │    ├─ llm.ainvoke(messages)
  │    │    → tool_calls: [{name: "code_exec", args: {code: "def quicksort..."}}]
  │    ├─ _execute_tool("code_exec", ...) → "Execution OK"
  │    ├─ llm.ainvoke([...ToolMessage("Execution OK")])
  │    │    → "快速排序已实现并通过测试"
  │    └─ step_outputs[2] = "快速排序已实现..."
  │
  └─ Step 3: "测试验证" (depends_on=[2])
       ├─ 同 step 2 流程
       └─ final = "所有测试通过"

Phase 3: 后处理
─────────────────────────────────────────────────────
  ├─ save_turn(task, final)
  ├─ asyncio.create_task(extract_facts_async)
  └─ state.turn_count += 1

最终输出: "所有测试通过"
```

## 4. Tool Calling 原理

### 4.1 整体流程

```
AgentRuntime.run()
  ├─ resolve_tools(skill_names)               ← ToolResolver: Skill → Tool 匹配
  ├─ bind_tools_to_llm()                      ← llm.bind_tools(tools)
  ├─ build_messages(task, system_prompt)       ← [System, History, Human]
  └─ _invoke_with_tool_loop(llm, messages)
       │
       while iteration < max_iterations:       ← 防死循环
         ├─ response = await llm.ainvoke(messages)
         │    → response.tool_calls = [
         │        {name: "code_exec", args: {code: "..."}, id: "call_1"},
         │        {name: "file_ops", args: {op: "write", path: "/a.py"}, id: "call_2"}
         │      ]
         │
         ├─ if not tool_calls: return response.content   ← 无工具 → 结束
         │
         ├─ messages.append(response)
         │
         ├─ for each tool_call:                           ← 串行执行 (V2 限制)
         │    ├─ tool = _tools.get(name)
         │    ├─ result = await tool.ainvoke(args)
         │    └─ messages.append(ToolMessage(result))
         │
         └─ iteration += 1 → loop

       return "[已取消]" 或 超限消息
```

### 4.2 关键设计决策

**为什么串行执行工具？**

Haven V2 串行执行 `tool_calls`（而非并行 `asyncio.gather`）。原因：

1. **依赖关系未知** — LLM 返回的 tool_calls 可能有隐式依赖（先读文件再写文件），框架无法判断
2. **副作用安全** — 并行执行两个写文件操作可能导致竞态条件
3. **未来方向** — 可以在 tool metadata 中声明 `parallelizable: true` 来标记可并行工具

**为什么有 max_iterations？**

防止 DDoS 自己。LLM 可能陷入工具调用死循环：

```
LLM: 调用 web_search("Python")
结果: "未找到关于 Python 的信息"
LLM: 调用 web_search("Python")
结果: "未找到关于 Python 的信息"
...
```

`max_iterations=20` 是一个保守但安全的默认值。

### 4.3 ToolResolver — 5 级匹配引擎

```
Skill.tools: ["code_exec", "file_ops"]
  │
  ▼
ToolResolver.resolve(["coder"])
  │
  ├─ Level 1: 精确名称匹配    "code_exec" → _name_index["code_exec"] → HavenTool
  ├─ Level 2: MCP 命名空间     "github__search_code" → 按名查找 MCP 工具
  ├─ Level 3: 标签匹配         "code_exec" → _tag_index["code_exec"] → 候选
  ├─ Level 4: 类别匹配         "code" → _category_index["code"] → 候选
  └─ Level 5: 能力关键词       "search" → _CAPABILITY_CATEGORY["search"]
                                     → ToolCategory.SEARCH
                                     → _category_index["search"] → 候选
```

**设计原理：** 让 Skill 作者不需要知道内部工具名。Skill 中可以写 `tools: ["search"]` 而不是 `tools: ["web_search_engine_bing_v3"]`。Resolver 负责"理解你想做什么"然后匹配到"哪个工具能做到"。

## 5. ExecutionPlan 的价值

### 5.1 为什么需要结构化规划

直接让 LLM 执行任务的问题：

```
用户: "帮我分析这个 CSV 里的销售数据，画个图表，写个报告"
LLM: (生成代码) → 执行 → 输出 → 但忽略了"画图表"
```

LLM 是单线程的——它一次只能做一件事。复杂任务需要分解。

### 5.2 ExecutionPlan 的数据结构

```python
class ExecutionPlan(BaseModel):
    goal: str                         # "分析销售 CSV 并生成报告"
    intent: str                       # "data" — 从 skill tags 中动态获取
    complexity: str                   # "complex" — simple | medium | complex
    skills: list[str]                 # ["data_analysis", "summarization"]
    workflow: str | None              # null — 无预定义工作流匹配
    steps: list[PlanStep]             # 3 个步骤，带依赖关系

class PlanStep(BaseModel):
    order: int                        # 1, 2, 3
    description: str                  # "读取并分析 CSV"
    skill: str | None                 # "data_analysis"
    depends_on: list[int]             # [] / [1] / [1, 2]
    expected_output: str              # "数据摘要和关键趋势"
```

### 5.3 关键价值

**1. 复杂度路由**

```
complexity = "simple"  → 1 step, Runtime.astream() 直通
complexity = "medium"  → 2-3 steps, 拓扑排序后串行执行
complexity = "complex" → 多步 + 依赖, WorkflowGraph.run() DAG 引擎
```

**2. 依赖管理**

```python
# _topological_sort 确保依赖关系
steps = [
    PlanStep(order=1, depends_on=[]),           # 可立即执行
    PlanStep(order=3, depends_on=[1, 2]),       # 等 1 和 2 完成
    PlanStep(order=2, depends_on=[1]),          # 等 1 完成
]
sorted = _topological_sort(steps) → [1, 2, 3]
```

**3. 一次性 LLM 调用替代多次**

V1 的流程：
```
LLM 调用 1: 分类意图 → "development"
LLM 调用 2: 选择 Skill → "coder"
LLM 调用 3: 拆解步骤 → [{step1}, {step2}]
```

V2 的流程：
```
LLM 调用 1: with_structured_output(ExecutionPlan) → 一次性全部输出
```

省掉了两次 LLM 调用，降低了延迟和成本。

## 6. Claude Code 和 Haven 的区别

| 维度 | Haven V2 | Claude Code |
|------|----------|-------------|
| **定位** | Agent 框架 (给开发者用) | 终端工具 (给用户用) |
| **架构** | Planner + Runtime 分离 | 单一 Agent 循环 |
| **规划方式** | 一次 LLM 调用 → 完整 ExecutionPlan | 逐步推理 (Think → Act → Observe) |
| **工具系统** | Provider 架构 + ToolResolver 5 级匹配 | 内置工具集 (Bash, Read, Write, Edit...) |
| **记忆** | 4 层持久化 (SQLite + ChromaDB) | 文件持久化 + CLAUDE.md |
| **工作流** | DAG 引擎 + 3 预定义拓扑 | Plan agent + TaskCreate/TaskUpdate |
| **多 Agent** | 无 (单 Planner) | Agent 工具 spawn 子 agent |
| **隔离** | 本地进程 | Worktree 沙箱 |
| **流式** | 原生 llm.astream() | 原生 |
| **扩展** | .md Skill + MCP | CLAUDE.md + MCP + Hooks |

**核心差异：** Claude Code 是"做事情的工具"，Haven 是"构建 Agent 的框架"。Claude Code 的架构更偏向用户体验（Hook/Cron/Worktree），Haven 的架构更偏向开发者扩展（Provider/Skill/Resolver/Workflow）。

## 7. Cursor 和 Haven 的区别

| 维度 | Haven V2 | Cursor |
|------|----------|--------|
| **平台** | Python CLI 框架 | TypeScript VS Code 扩展 |
| **上下文** | ContextManager 6 源收集 | VS Code 原生 API (editor, terminal, LSP, file tree) |
| **代码编辑** | FileOpsTool (文件级) | 内联 diff apply (行级) |
| **工具** | Provider 架构 + MCP | VS Code 扩展 API + MCP |
| **记忆** | 4 层持久化 | 会话上下文 + .cursorrules |
| **工作流** | 固定 DAG 模板 | Agent 内联处理 |
| **RAG** | RAGSearchTool (通用) | @Codebase / @Docs (代码语义索引) |
| **多通道** | CLI + Socket + Email + 飞书 | IDE 内 |

**核心差异：** Cursor 的上下文来自 IDE（编辑器状态、LSP 诊断、终端输出），Haven 的上下文来自框架自身（Memory/Skill/Workflow）。Cursor 不需要"记忆系统"因为 IDE 本身就是上下文源，Haven 需要因为它是独立运行的 Agent。

## 8. 面试常见问题

### Q1: Agent Runtime 和普通 LLM 调用的区别是什么？

**答：** LLM 调用是 `llm.ainvoke(messages)` — 一问一答。Agent Runtime 在这之上加了四层：

1. **工具循环** — LLM 可以"请求执行工具"，Runtime 执行后把结果传回去，循环到 LLM 不再请求工具
2. **上下文组装** — 每次调用前从 Memory/Skill/Workflow 等多源收集上下文
3. **重试恢复** — 网络错误自动 exponential backoff + jitter 重试
4. **状态追踪** — ExecutionState 追踪每个步骤的成败

### Q2: 为什么 Planner 和 Runtime 要分开？

**答：** 见第 2 节。核心是**单一职责 + 可测试性 + 路径可替换**。

### Q3: ToolResolver 的 5 级匹配有什么用？

**答：** 解耦 Skill 和 Tool。Skill 作者写 `tools: ["search"]` 就够了，不需要知道工具叫 `web_search` 还是 `bing_search_v3`。Resolved 负责"理解意图 → 找到最佳实现"。

### Q4: 3 条执行路径怎么选择？

**答：** Planner 的 `execute()` 根据 ExecutionPlan 自动路由：

```
workflow != null?  → 路径 1: WorkflowGraph.run()
steps > 0?         → 路径 2: _execute_steps() 拓扑排序后执行
否则                → 路径 3: Runtime.run() 直通
```

### Q5: 为什么没有多 Agent？

**答：** V2 的定位是"单 Agent 框架做对"再考虑多 Agent。多 Agent 引入了通信协议、任务分配、结果合并等复杂度，在没有解决单 Agent 可靠性问题之前做多 Agent 是过早优化。

### Q6: ExecutionPlan 的 LLM Structured Output 可靠性如何？

**答：** 通过 `with_structured_output(ExecutionPlan)` 强制 JSON Schema 约束。LLM 无法输出不符合 schema 的结果。如果 LLM 调用本身失败（网络错误等），有 fallback plan：

```python
try:
    plan = await structured_llm.ainvoke(...)
except Exception:
    plan = ExecutionPlan(intent="chat", complexity="simple", steps=[])
```

## 9. 如何在简历中描述该架构

### 版本 A: 简洁 (1 行)

> 设计并实现了基于 Planner-Runtime 分离架构的多智能体交互框架，支持 LLM Structured Output 自动任务规划、5 级工具动态匹配、DAG 工作流引擎。

### 版本 B: 展开 (3-5 行)

> Haven V2 Agent Runtime 架构设计：
>
> - **PlannerAgent** — LLM Structured Output 单次调用完成意图分类 + Skill 选择 + 步骤拆解 + Workflow 匹配，3 条执行路径自动路由
> - **AgentRuntime** — 纯执行引擎，组合 LLM + Tool + Memory + State + Context，含工具调用循环、exponential backoff 重试、原生流式输出
> - **ToolResolver** — 5 级动态匹配引擎 (精确名称 → MCP 命名空间 → 标签 → 类别 → 能力关键词)，解耦 Skill 声明与 Tool 实现
> - **ExecutionPlan** — Pydantic 结构化规划输出，支持拓扑排序依赖管理、ExecutionState 任务级生命周期追踪
> - **ContextManager** — 6 源上下文编排 (人格/技能/记忆/工作流/工具/RAG)，TokenBudget 分级裁剪

### 版本 C: 详细 (项目描述)

> Haven 是个人项目，定位为 AI Agent 框架。实现了完整的 Agent Runtime 架构：
>
> **规划层：** PlannerAgent 使用 LangChain `with_structured_output` 将 LLM 输出约束为 `ExecutionPlan` Pydantic 模型（包含 goal、intent、complexity、skills、workflow、steps），一次调用完成传统方案需 2-3 次 LLM 调用才能完成的任务规划。
>
> **执行层：** AgentRuntime 纯执行引擎，支持带工具调用循环的 LLM 调用（最多 20 轮迭代 + exponential backoff 重试）、原生 llm.astream 流式输出、ExecutionContext 外部取消。
>
> **工具系统：** ToolManager + Provider 架构（Builtin 6 工具 + MCP 协议集成），ToolResolver 5 级匹配支持能力关键词到工具实现的动态解析。
>
> **工作流引擎：** 自研 DAG 引擎 (WorkflowGraph)，支持无条件边 + 条件边 + RETRY sentinel + SQLite Checkpoint 持久化，3 个预定义工作流 (dev/research/diagnosis)。
>
> 项目使用 Ruff + Mypy + pytest (270 个测试，73% 核心模块覆盖率) + GitHub Actions CI。
