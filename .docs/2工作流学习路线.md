# Haven Workflow 系统 — 作者学习路线

> 目标：独立讲清楚 DAG 工作流引擎的工程价值，对比 LangGraph/CrewAI 的设计差异。
> 读者定位：框架开发者，重点讲架构决策而非 API 教学。

## 1. Workflow 的本质

### 1.1 Workflow 与 Agent 的区别

这是面试中最容易被问倒的问题。很多人把两者混为一谈。

| | Agent | Workflow |
|---|---|---|
| **执行模型** | 自由探索 (LLM 自主决策下一步) | 固定拓扑 (预定义 DAG) |
| **控制权** | LLM 决定做什么 | 开发者决定执行顺序 |
| **可靠性** | 不确定 (LLM 可能走偏) | 确定 (图结构保证路径) |
| **适用场景** | 开放式任务 (聊天、探索) | 结构化任务 (开发流水线、诊断流程) |
| **调试难度** | 高 (自由探索不可预测) | 低 (执行路径可复现) |

**一个例子讲清楚：**

```
Agent 模式 (Runtime.run):
  用户: "帮我优化这个函数"
  LLM: 我看看... 先读代码 → 分析 → 改写 → 测试 → 完成
  (LLM 自己决定每一步做什么)

Workflow 模式 (WorkflowGraph.run):
  用户: "帮我写一个登录模块"
  planner → architect → coder → reviewer → tester
  (每一步做什么是图定义的，LLM 只负责执行每个节点的 prompt)
```

**关键洞察：Agent 适合"我不确定要做什么"的任务，Workflow 适合"我知道流程，但每步需要 AI 能力"的任务。**

### 1.2 DAG 为什么存在

DAG = Directed Acyclic Graph = 有向无环图。

**为什么不是简单的顺序列表？**

```
# 顺序列表 — 无法表达并行
step1 → step2 → step3 → step4

# DAG — 可以表达并行 + 依赖
     step1
    /      \
step2    step3    ← 2 和 3 可以并行 (都只依赖 1)
    \      /
     step4        ← 4 需要等 2 和 3 都完成
```

**为什么不是树 (Tree)？**

树要求每个节点只有一个父节点。DAG 允许一个节点有多个父节点（汇聚点），这在工程流中很常见：

```
需求分析 → 前端设计 → 前端实现 ──┐
                                  ├→ 集成测试 → 完成
需求分析 → 后端设计 → 后端实现 ──┘
```

**为什么不能有环？**

环 = 死循环。如果没有环检测，执行引擎会永远运行。Haven 用 `max_iterations=20` 兜底，但 graph 规范要求是 DAG（RETRY 是唯一的"伪环"）。

## 2. DAG 执行模型

### 2.1 Haven WorkflowGraph 的核心数据结构

```python
class WorkflowGraph:
    _nodes: dict[str, Any]           # {"planner": PlannerNode(), ...}
    _edges: dict[str, Edge]          # {"planner": Edge("planner","coder"), ...}
    _entry_point: str                # "planner"
    _checkpointer: Checkpointer      # SQLiteCheckpointer
    _max_iterations: int             # 20
```

**为什么用字典而非邻接表？**

每个节点最多一条出边。如果不需要多出边，字典比邻接表更简单：

```python
# 邻接表 (LangGraph 的做法 — 支持多出边)
edges = {"planner": ["coder"], "coder": ["reviewer", "tester"]}

# 字典 (Haven 的做法 — 每条边支持分支)
edges = {"planner": Edge("planner", "coder"),
         "coder": ConditionalEdge("coder", router)}
```

Haven 选择字典 + ConditionalEdge 的方式：简单节点用 `Edge`（单目标），分支节点用 `ConditionalEdge`（Router 函数动态决定目标）。

### 2.2 执行循环

```python
current = entry_point
while current != END and iteration < max_iterations:
    1. 取消检查 → cancelled? break
    2. 执行节点 → updates = await node(state)
    3. 合并更新 → _apply_updates(state, updates)
    4. 失败检查 → es.status == "failed"? break
    5. 持久化   → checkpoint.save(state)
    6. 确定下一步 → edge.resolve(state) → next_node
    7. 重试检查 → next_node == RETRY? 检查 retries < max
    8. current = next_node
```

**为什么每步都要 checkpoint？**

因为 LLM 调用是最昂贵的操作（时间 + 成本）。一个 5 节点工作流中 LLM 调用 3 次，如果第 4 步失败，从头开始重跑 3 次 LLM 调用是不可接受的。每步 check point 意味着**失败后从断点继续**，而不是从头开始。

### 2.3 两条边类型

**Edge (无条件边):**

```python
class Edge:
    source: str  # "planner"
    target: str  # "coder"
```
一个完成后必然到下一个。最常用的类型。

**ConditionalEdge (条件边):**

```python
class ConditionalEdge:
    source: str                        # "tester"
    router: Callable[[State], str]     # Router 函数
    route_map: dict[str, str]          # {"coder": "coder", "done": "__END__"}
```

Router 函数接收当前 state，返回下一步节点名。典型例子：

```python
def test_router(state):
    if state.test_passed:
        return ConditionalEdge.END    # 测试通过 → 结束
    if retries < max_retries:
        return "coder"                 # 测试失败 → 重新编码
    return ConditionalEdge.END         # 超限 → 结束
```

## 3. Checkpoint 原理

### 3.1 为什么需要 Checkpoint

典型的开发工作流 (5 节点)：

```
planner → architect → coder → reviewer → tester
```

场景： reviewer 执行到一半，LLM 返回 rate limit 错误。

没有 Checkpoint：整个任务从头重跑（planner + architect + coder 的 LLM 调用全部浪费）。

有 Checkpoint：从 reviewer 的断点恢复。

### 3.2 Haven 的实现

**存储结构：**

```sql
CREATE TABLE workflow_checkpoints (
    session_id TEXT NOT NULL,          -- 会话 ID
    node_name TEXT NOT NULL,           -- 当前节点名
    state_json TEXT NOT NULL,          -- 完整 WorkflowState (JSON)
    execution_json TEXT,               -- ExecutionState 快照 (单独列)
    created_at TIMESTAMP,
    UNIQUE(session_id, node_name)      -- 同 session+node 只保留最新
);
```

**两列 JSON 的分工：**

- `state_json`: 完整的 WorkflowState 序列化，包含领域字段 (architecture_doc, source_code...) 和消息历史
- `execution_json`: ExecutionState.snapshot() 单独存一列，方便恢复时快速定位 `current_step` 和 `retry_counts`

**保存时机：**

```
每个节点执行完成后 → checkpoint.save(session_id, node_name, state)
工作流正常结束 (END) → checkpoint.save(session_id, "__END__", state)
```

**恢复流程：**

```python
# graph.run(resume_from="session_abc")
saved = await checkpointer.load("session_abc")
state.execution = saved["execution"]  # 恢复 ExecutionState 对象
current = es.current_step             # 从断点继续
```

### 3.3 UPSERT 语义

```sql
INSERT INTO workflow_checkpoints (...) VALUES (...)
ON CONFLICT(session_id, node_name) DO UPDATE SET
    state_json = excluded.state_json,
    execution_json = excluded.execution_json,
    created_at = CURRENT_TIMESTAMP
```

为什么是 UPSERT 而不是 INSERT？因为同一个 session 的同一个 node 可能被多次执行（RETRY 场景）。每次执行后应该更新而非新增。

## 4. Retry 原理

### 4.1 两层重试架构

```
L1: LLM 调用重试      ← core/retry.py (exponential backoff)
    └─ 网络错误、rate limit、5xx → 自动重试 (max 3 次)

L2: 节点级重试         ← WorkflowGraph RETRY sentinel
    └─ 业务逻辑失败 (测试不通过、review 不通过) → Router 返回 RETRY
    └─ node_retry_counts 追踪每节点重试次数
```

**为什么需要两层？**

L1 处理的是**基础设施故障**（网络断了、LLM 服务崩了）。Runtime 层面自动重试，节点不需要感知。

L2 处理的是**业务逻辑失败**（代码不通过测试、设计被 review 打回）。这些不是"系统错误"，而是"输出质量不达标"。需要节点重新执行——通常带上反馈信息。

### 4.2 RETRY 在 DAG 中的实现

```python
# edges.py: ConditionalEdge.RETRY = "__RETRY__"

# graph.py run loop:
if next_node == ConditionalEdge.RETRY:
    retries = es.node_retry_counts.get(current, 0)
    if retries < es.max_retries:
        next_node = current          # 回跳到当前节点
    else:
        es.fail(...)                 # 超过最大重试 → 失败
```

**关键细节：RETRY 是唯一的"伪环"。** 正常的 DAG 不允许环，但 RETRY 允许节点指向自己——因为每次重试都带着新的上下文（上一次的反馈），不是简单的重复。

### 4.3 Retry 上下文传递

```python
class CoderNode:
    def _build_prompt(self, state):
        parts = ["编写代码", f"需求: {state.task}"]

        # 重试时注入上次的反馈
        if state.node_retry_counts.get("coder", 0) > 0:
            if review_feedback:
                parts.append(f"Review 反馈: {review_feedback}")
            if test_failures:
                parts.append("测试失败: " + "\n".join(test_failures))
            parts.append("请修正所有问题后重新生成代码。")

        return "\n".join(parts)
```

这解释了为什么 RETRY 不是简单的"再来一次"——每次重试带有**递增的上下文**（review 反馈、测试失败信息），输出质量应该逐步提升。

## 5. LangGraph 为什么流行 + Haven 对比

### 5.1 LangGraph 的核心思想

LangGraph 解决了 Agent 框架的一个根本问题：**ReAct 模式不可控。**

```
# ReAct (自由探索)
LLM think → act → observe → think → act → observe → ...

问题: LLM 可能永远不停止，或者做出错误的路径选择
```

LangGraph 的答案：**用图约束 Agent 的执行路径。**

```
# LangGraph 风格
entry → node1 → (conditional) → node2a / node2b → end
```

LangGraph 本质上是一个**带状态的图执行引擎**，可以把 Agent 的每一步限制在预定义的路径上。关键概念：

- **State**: 全局共享状态，在节点间传递
- **Node**: Python 函数 `(state) → update_dict`
- **Edge**: 普通边 (固定跳转) / 条件边 (Router 函数)
- **Checkpointer**: 每步自动持久化，支持 human-in-the-loop 和中断恢复

### 5.2 Haven WorkflowGraph vs LangGraph

| 维度 | Haven WorkflowGraph | LangGraph |
|------|-------------------|-----------|
| **节点签名** | `(state) → dict` | `(state) → dict` |
| **边类型** | Edge + ConditionalEdge | add_edge + add_conditional_edges |
| **状态** | WorkflowState (dataclass) | TypedDict / Pydantic |
| **Checkpoint** | SQLiteCheckpointer (自研) | SqliteSaver / PostgresSaver |
| **流式** | 通过 Runtime.astream 直通 | astream_events 原生 |
| **多图组合** | 不支持 | StateGraph.compile() + subgraph |
| **Human-in-the-loop** | 不支持 (未实现) | interrupt_before / interrupt_after |
| **并行节点** | 不支持 (串行) | Send API 扇出 |
| **运行时** | 内置 AgentRuntime | 需要用户自己组装 LLM 调用 |
| **代码量** | ~285 行 | ~10,000+ 行 |

**核心差异：**

Haven 的 WorkflowGraph 是 **Agent Runtime 的扩展层**——节点内部调用 `runtime.run()`，所以每个节点自动获得 LLM + Tool + Memory + Context 的全部能力。

LangGraph 是一个**纯图执行引擎**——节点是普通 Python 函数，如果要调 LLM 需要用户自己实现。LangGraph 不关心节点里做什么。

**工程价值判断：**

- Haven 的 WorkflowGraph 更适合**快速构建 Agent 工作流**（开发者不需要处理 LLM 调用细节）
- LangGraph 更适合**需要精细控制的复杂图**（多图组合、human-in-the-loop、并行扇出）

## 6. 与 CrewAI Flow 对比

CrewAI 是另一个流行的 Python Agent 框架。2024 年底推出了 Flow 功能。

| 维度 | Haven WorkflowGraph | CrewAI Flow |
|------|-------------------|-------------|
| **执行模型** | DAG (有向无环图) | 事件驱动 (Event-Driven) |
| **状态管理** | WorkflowState + ExecutionState | FlowState (dict-like) |
| **条件路由** | ConditionalEdge + Router 函数 | `@listen(condition)` 装饰器 |
| **并行** | 不支持 (串行 DAG) | 支持 (事件广播 → 多 listener) |
| **Checkpoint** | SQLite (自研) | 不支持 (内存) |
| **重试** | RETRY sentinel (图级) | `@retry` 装饰器 (节点级) |
| **人机交互** | 不支持 | 支持 `human_input()` |
| **Agent 集成** | Runtime.run() 内嵌 | Crew + Agent + Task 模式 |

**核心差异：执行模型。**

Haven 是**拓扑驱动**：节点按 DAG 的边关系顺序执行。适合"我知道流程"的场景。

CrewAI Flow 是**事件驱动**：节点监听事件，事件触发时执行。适合"不确定什么时候发生"的场景。

**工程价值判断：**

- DAG 简单直接，调试容易（执行路径可预测）
- 事件驱动更灵活，但调试困难（事件触发链难以追踪）

## 7. 当前设计优缺点

### 优点

1. **简单** — 285 行核心代码实现完整的 DAG 引擎 + Checkpoint + Retry + Cancel。开发者 30 分钟能读完源码。

2. **与 Runtime 深度集成** — 节点内部直接调用 `runtime.run()`，每个节点自动获得 LLM + Tool + Memory + Context 能力。不需要像 LangGraph 那样在节点里手动组装 prompt 和调 LLM。

3. **双写模式** — `_apply_updates` 同时写入 `state.*` 和 `execution.*`。WorkflowState 保留旧字段向后兼容，ExecutionState 作为权威源。

4. **Checkpoint 设计** — `execution_json` 单独列 + UPSERT 语义，恢复时直接从 ExecutionState 快照重建。

5. **RETRY sentinel** — 把"重试"伪装成"边"，不破坏 DAG 的语义纯净性。

### 缺点

1. **每个节点单出边** — 如果需要扇形展开（一个节点后分 3 路并行），当前 `_edges` 字典只能存一条边。需要用 ConditionalEdge 变通，不够优雅。

2. **无并行执行** — DAG 天然支持并行节点（同一层无依赖的节点可以并发），但当前实现是严格串行的。

3. **无 Human-in-the-loop** — 无法在某个节点执行前暂停等用户输入。这是 LangGraph 的一大卖点。

4. **图不可组合** — 无法将一个图作为另一个图的子图。LangGraph 的 `compile()` 和图嵌套能力在这方面更成熟。

5. **节点与 Skill 耦合** — `CoderNode.skill_name = "coder"` 是硬编码的。如果想把同一个节点用于不同的 skill，需要创建子类。

## 8. 面试常见问题

### Q1: Agent 和 Workflow 的区别？什么时候用哪个？

**答：** Agent 是自由探索模式（LLM 决定下一步），Workflow 是固定拓扑模式（图决定执行顺序）。

判断标准：**你需要的结果是否可预测？**

- 可预测（"这个需求必须经过需求分析→架构→编码→审查→测试"）→ Workflow
- 不可预测（"帮我研究一下 X 领域的前沿进展"）→ Agent

实践中，成熟的 Agent 系统二者都会用到。Haven 的 Planner 自动路由：匹配到预定义工作流就走 DAG，否则走 Agent 自由探索。

### Q2: 为什么用 DAG 而不是状态机？

**答：** DAG 是状态机的一个子集。状态机可以表达 DAG 无法表达的东西（如循环、任意跳转），但代价是**不可预测性**。

Agent 场景中"不可预测"是很糟糕的——你不知道一个任务要执行多久、花多少 LLM 调用的钱。DAG 在灵活性和可控性之间找到了平衡点。

### Q3: 为什么每个节点返回 dict 而不是直接修改 state？

**答：** 这是 LangGraph 的核心设计模式 — **不可变性 + 声明式更新**。

```python
# 反模式 (直接修改 state)
async def node(state):
    state.source_code = "..."    # 副作用，难以追踪

# 正确 (声明式更新)
async def node(state):
    return {"source_code": "..."}  # 清晰表达 "我改了 source_code"
```

好处：
1. 执行引擎可以追踪每个节点的所有变更（日志、审计）
2. 可以决定哪些变更写入 state.execution，哪些只写 state
3. 节点可测试（输入 state → 验证输出 dict）

### Q4: Checkpoint 为什么不存内存？

**答：** 进程重启后内存丢失。Workflow 可能需要几十分钟（多个 LLM 调用），如果进程崩溃后无法恢复，前面的 LLM 调用费用全部浪费。SQLite 持久化意味着进程重启后可以 `resume_from="session_abc"` 继续。

### Q5: Haven 的 WorkflowGraph 和 LangGraph 比差在哪？

**答：** 见第 5.2 节对比表。最核心的三个差距：

1. 不支持并行节点（LangGraph 的 Send API）
2. 不支持 Human-in-the-loop（LangGraph 的 interrupt）
3. 不支持子图组合（LangGraph 的 compile）

但 Haven 的优势在于代码量少 30 倍 + 与 AgentRuntime 深度集成。对于中小规模的工作流，Haven 的简单性是一个优势。

>
