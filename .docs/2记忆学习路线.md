# Haven Memory 系统 — 作者学习路线

> 目标：独立讲清楚 Agent Memory 的四层架构，面试能深入回答每层的设计决策和工程实现。
> 读者定位：开发者（非 AI 研究员），重点讲工程实现。

---

## 1. 先搞清楚：为什么需要 Memory

### 问题：无 Memory 的 Agent 长什么样

```
用户: 我叫张三，我对猫过敏。
Agent: 你好张三！记住了。

用户: (第二天) 我朋友送了我一只猫。
Agent: 恭喜！猫很可爱。
```

没有 Memory，Agent 每次对话都是**从零开始**。System prompt + 当前消息 → LLM 推理。无论聊了多少轮，LLM 眼里永远只有当前窗口内的内容。

### 聊天记录 != Agent Memory

这是面试中最重要的区分：

| | 聊天记录 (Chat History) | Agent Memory |
|---|---|---|
| **存储方式** | LangChain `messages: list[BaseMessage]` | 结构化分层存储 |
| **生命周期** | 单次会话 | 跨会话持久化 |
| **检索方式** | 顺序追加 | 关键词 + 语义 + 时间衰减 |
| **数据形态** | 原始对话文本 | 提取的事实 + 嵌入向量 |
| **典型问题** | token 成本线性增长 | 查询复杂度 O(1) / O(log n) |

**总结一句话：聊天记录是"一字不漏记下来"，Memory 是"理解后记住重要的事"。**

---

## 2. 当前实现原理

Haven V2 Memory 架构 = **四层分治 + 统一编排**。

```
                     MemoryManager (编排层)
                    ┌──────────────────────┐
                    │  record_turn()        │  ← 存储入口
                    │  retrieve()           │  ← 检索入口
                    │  consolidate()        │  ← 后台维护
                    └──────┬───────────────┘
           ┌───────────────┼───────────────┐
           │               │               │
    ┌──────▼──────┐ ┌──────▼──────┐ ┌──────▼──────┐
    │  Working    │ │  Episodic   │ │  Semantic   │  (必有)
    │  (内存)     │ │  (SQLite)   │ │  (SQLite)   │
    └─────────────┘ └─────────────┘ └─────────────┘
                                           │
                                    ┌──────▼──────┐
                                    │   Vector    │  (可选)
                                    │  (ChromaDB) │
                                    └─────────────┘
```

**关键设计决策：AgentMemory 是 V1 兼容 facade，内部全部委托给 MemoryManager。**

下面逐层分析。

## 3. 每层 Memory 的职责与实现

### 3.1 WorkingMemory — 会话内滑动窗口

**一句话：当前对话的短期记忆。**

```python
# 核心数据结构 (working.py:27-32)
self.sliding_window: deque[BaseMessage]   # deque(maxlen=100) 自动淘汰
self.pinned_items: list[MemoryItem]       # 钉选重要信息，始终保留
self.summary: str                         # 超出窗口的消息摘要
self._summary_buffer: list[BaseMessage]   # 被淘汰的消息暂存
```

**存储：** 进程内存，不持久化。Python `deque(maxlen=100)`。

**写入 (add_message)：**
```
append(message) → 窗口未满 → 保留
               → 窗口已满 → pop 最旧消息 → 移入 _summary_buffer
```

**摘要触发 (needs_summarization)：**
```
_summary_buffer 累积 ≥ 10 条 → LLM 调用 summarize()
                              → 生成 ≤200 字中文摘要
                              → 清空 buffer
```

**检索：** 返回最近 N 条消息 + pinned_items。不参与 system prompt 注入，直接追加到 messages 列表。

**面试要点：**
- 为什么用 deque 而不是 list？deque O(1) 头尾操作，maxlen 自动淘汰。
- 为什么需要摘要？100 轮对话 ≈ 5K-20K tokens，超出 LLM 上下文窗口时需要压缩。
- pinned_items 的用途：像"用户姓名""过敏信息"这种即使超出窗口也不能丢的键信息。

### 3.2 EpisodicMemory — 完整对话记录

**一句话：跨会话的对话日志，带时间衰减 + 重要性加权的检索。**

```sql
-- 核心表 (episodic.py:38-54)
CREATE TABLE episodes (
    id TEXT PRIMARY KEY,
    session_id TEXT NOT NULL,        -- 会话标识
    turn_number INTEGER NOT NULL,    -- 第几轮
    user_message TEXT NOT NULL,      -- 用户说的话
    assistant_response TEXT NOT NULL, -- AI 的回复
    importance REAL DEFAULT 0.5,     -- 重要性 0.0~1.0
    created_at TIMESTAMP
);
```

**存储：** SQLite，与 SemanticMemory 共享 `memory.db`，不同表。

**三层检索模式：**

| 模式 | SQL | 场景 |
|------|-----|------|
| `recent` | `ORDER BY created_at DESC` | "刚才聊了什么" |
| `keyword` | `WHERE content LIKE '%keyword%'` | "之前提到过 Python 吗" |
| `hybrid` | `importance*0.6 + 1/(days_ago+1)*0.4` | 综合排序 (默认) |

**hybrid 排序公式：**
```
score = importance × 0.6 + (1 / (days_since_created + 1)) × 0.4
```
越重要、越近 → 排名越高。超过 30 天自动排除 (time_range="30d")。

**Consolidation (后台维护)：**
```
每天运行一次 → 扫描 summary 为空的旧对话 (超过 1 天)
              → LLM 生成一句话摘要
              → 写入 summary 字段
```

**面试要点：**
- 为什么 importance 权重 0.6 而不是 0.5？工程经验：重要性比时间更稳定。上周聊过的技术问题可能今天还需要，但上周的闲聊不需要。
- 为什么用 SQLite 而不是 PostgreSQL？Agent 场景下数据量在 GB 以内，SQLite 零运维 + 嵌入式部署。
- `check_same_thread=False` 的必要性：asyncio 中不同 task 可能在不同线程执行。

### 3.3 SemanticMemory — 结构化知识图

**一句话：从对话中提取结构化事实，形成"实体-事实-历史"三层知识图。**

```sql
-- 三张核心表 (semantic.py:40-73)
memory_entities      -- 实体: {id: 1, name: "张三", type: "user"}
memory_facts         -- 事实: {entity_id: 1, key: "allergy", value: "猫",
                     --        confidence: 0.9, tags: ["health"]}
memory_fact_history  -- 变更历史: {fact_id: 5, old_value: "Java",
                     --             new_value: "Python"}
```

**写入流程：**

```
对话: "我现在主要用 Python 开发"
  ↓ LLM 提取 (memory/manager.py:218-260)
  ↓ prompt: "提取关于当前用户的结构化信息，返回 JSON"
  ↓ LLM 返回: {"facts": [{"key": "primary_lang", "value": "Python",
  ↓                       "confidence": 0.9, "tags": ["skill"]}]}
  ↓
  ↓ _get_or_create_entity("张三", "user") → entity_id=1
  ↓ _get_fact_value(1, "primary_lang") → 旧值是 "Java" 还是 None?
  ↓
  ├─ 无旧值 → INSERT memory_facts
  └─ 有旧值 → _record_history (存档旧值)
             → UPDATE memory_facts (UPSERT)
```

**事实变更追踪：**
```
T1: 用户说 "我用 Java"    → facts: {primary_lang: "Java"}
T5: 用户说 "我改用 Python" → history: {old: "Java", new: "Python"}
                           → facts: {primary_lang: "Python"}
```
这点在面试中特别有说服力——不只是"存知识"，而是"追踪知识演变"。

**Confidence 置信度：**
- 初始值：LLM 评估 (明确陈述 → 0.9，暗示 → 0.5)
- 衰减：consolidate() 每 10 轮执行一次
  - 超过 30 天的低置信度事实 → `confidence -= 0.1`
  - 低于 0.1 → 自动删除
- 注入 system prompt 的最低线：`confidence >= 0.3`

**事实提取触发：**
```python
# manager.py:122 — 每轮对话后异步触发
asyncio.create_task(self._extract_facts(user_message, assistant_message))
```
`create_task` 是关键——不阻塞主流程，后台 fire-and-forget。

**面试要点：**
- 为什么需要 confidence？用户说"我可能想学 Rust"和"我是 Rust 工程师"置信度不同。
- UPSERT + history 表 = 事实版本控制，像一个微型 git。
- 为什么不在 Semantic 里存对话原文？原文在 Episodic，Semantic 存结构化事实——分离关注点。

### 3.4 VectorMemory — 语义相似性检索

**一句话：超越关键词匹配，按"意思相近"检索。**

```python
# vector.py:27-35
self._client = chromadb.PersistentClient(path=".data/chroma/")
self._collection = client.get_or_create_collection(
    name="haven_memory",
    metadata={"hnsw:space": "cosine"}  # 余弦距离
)
```

**存储：** ChromaDB (持久化到 `.data/chroma/`)，每个条目存 `{id, embedding, document, metadata}`。

**Embedding 模型：** `text-embedding-3-small` (OpenAI 兼容 API)。

**检索流程：**
```
query: "我想了解编程语言"  →  _embedding_fn.aembed_query(query)
                            →  query_embedding (1536 维向量)
                            →  collection.query(query_embeddings=[...], n_results=5)
                            →  cosine 距离 → 相似度排序
                            →  返回 top-5
```

**降级策略：**
```python
# 三层 fallback
try:
    import chromadb  → 成功 → 正常使用
except ImportError:
    _client = False  → 静默降级 → store/retrieve 为空操作
except Exception:
    _client = False  → 静默降级
```

**Consolidation：** 超出 10000 条时删除最旧的 N 条，保持存储可控。

**面试要点：**
- 为什么需要 Vector？Episodic 和 Semantic 都是精确/keyword 匹配，Vector 处理"意思相近但用词不同"的查询。
- 为什么默认关闭？Embedding 调用有成本（API 调用 + token 消耗），不是所有场景都需要。
- cosine 距离 vs 欧氏距离：cosine 对文本长度不敏感，高频短文本更稳定。

## 4. 四层对比总表

| 维度 | Working | Episodic | Semantic | Vector |
|------|---------|----------|----------|--------|
| **存什么** | 最近 N 条消息 | 完整对话轮次 | 结构化事实 | 嵌入向量 |
| **存储介质** | 进程内存 | SQLite | SQLite | ChromaDB |
| **生命周期** | 会话内 | 持久化 | 持久化 | 持久化 |
| **检索方式** | 顺序取最近 | keyword + 时间衰减 + 重要性 | 实体/键/标签/置信度 | 语义相似度 |
| **写入速度** | 即时 | 同步 SQL | 异步 fire-and-forget | 异步 embed |
| **Token 成本** | 包含在 messages 中 | 注入 system prompt | 注入 system prompt | 注入 system prompt |
| **默认状态** | 始终启用 | 始终启用 | 始终启用 | **关闭** |

## 5. 数据流全景

```
record_turn(user: "我叫张三，对猫过敏", assistant: "好的张三，记住了")
  │
  ├─ [1] WorkingMemory.add_message()          ← 同步，追加到 deque
  ├─ [2] EpisodicMemory.store_turn()          ← 同步 SQL，完整存储
  ├─ [3] VectorMemory.store()                 ← 异步 embed → ChromaDB
  ├─ [4] asyncio.create_task(extract_facts)   ← 后台 LLM 提取事实
  │      └─ LLM 提取 {key: "name", value: "张三", confidence: 0.9}
  │      └─ LLM 提取 {key: "allergy", value: "猫", confidence: 0.9, tags: ["health"]}
  │      └─ SemanticMemory.store(items)       ← UPSERT facts
  ├─ [5] working.needs_summarization()?       ← buffer ≥ 10 时触发
  │      └─ asyncio.create_task(working.summarize(llm))
  └─ [6] 每 10 轮 → asyncio.create_task(consolidate())
         └─ Episodic: 旧对话摘要生成
         └─ Semantic: 低置信度事实衰减
         └─ Vector: 超出 10K 条清理

retrieve(task: "我朋友想送我宠物")
  │
  ├─ WorkingMemory.retrieve()     ← 最近 20 条
  ├─ EpisodicMemory.retrieve()    ← 30 天内 keyword "宠物" + importance ≥ 0.3
  ├─ SemanticMemory.retrieve()    ← entity_name="张三" + confidence ≥ 0.3
  │    └─ 返回: {allergy: "猫", confidence: 0.9}
  └─ VectorMemory.retrieve()      ← "宠物" 语义相似 top-5 (如果启用)
  │
  └─ MemoryContext {working, episodic, semantic, vector}
     └─ format_for_prompt() → 注入 system prompt
```

## 6. 面试常见问题 + 参考回答

### Q1: Agent Memory 与聊天记录的本质区别？

**答：** 聊天记录是"原样存"，Memory 是"理解后存"。

具体来说：聊天记录把每轮对话原封不动追加到列表，你检索时只能按时间顺序取最近 N 条。Memory 做了三件事：
1. **提取** — LLM 从对话中抽取结构化事实 (Semantic)
2. **压缩** — 超窗口的消息生成摘要 (Working)
3. **索引** — 按重要性 + 时间衰减 + 语义相似度多路检索 (Episodic/Vector)

工程上讲，聊天记录的 token 成本是 O(n)，Memory 降到了 O(1)。

### Q2: 为什么需要四层而不是一层？

**答：** 不同场景需要不同的检索策略。打个比方：

- 用户说"继续刚才的话题" → Working (最近的消息)
- 用户说"上周我们聊过微服务" → Episodic (关键词 + 时间范围)
- 用户说"我对什么过敏来着" → Semantic (结构化事实查询)
- 用户说"有什么类似的技术" → Vector (语义相似)

如果把这些全塞在一个表里，要么查询太慢，要么精度太差。分层之后每层只做一件精确的事。

**补充：** 实际工程中如果数据量小(<1000 条)，可以把 Episodic 和 Semantic 合在一张表。Haven 拆开是为了**未来扩展性**——当 Episodic 达到 10 万条时，Semantic 仍然只有几百条事实，检索不受影响。

### Q3: confidence 置信度是怎么用的？

**答：** 三个阶段：

1. **写入时** — LLM 评估事实的确定性。明确陈述 → 0.9，暗示 → 0.5。
2. **检索时** — `min_confidence >= 0.3` 过滤掉不确定的信息，避免误导 LLM。
3. **衰减时** — 超过 30 天且 confidence < 0.9 的事实 → `confidence -= 0.1`。低于 0.1 → 删除。

核心思路：用户随口提的信息会随时间自然遗忘，只有反复确认的信息才长期保留。

### Q4: 为什么 Vector 默认关闭？

**答：** 两个原因：

1. **成本** — Embedding API 每次调用有费用。如果用户主要问的是明确事实（"我上次的体检结果"），Semantic 就能回答，无需 Vector。
2. **启动依赖** — ChromaDB 需要额外安装。作为框架，不能假设用户一定有这个环境。降级策略确保核心功能不受影响。

打开方式：框架用户按需 `enable_vector=True`。

### Q5: 数据一致性怎么保证？

**答：** Haven 不追求强一致性，而是**最终一致性**。

- `record_turn()` 对 Episodic 同步写入（保证对话不丢失）
- Semantic 提取和 Vector embed 是异步的（`create_task`）
- 这意味着：对话结束后 Semantic 可能还没更新，但下一轮对话前大概率已完成

工程权衡：Agent 场景对延迟敏感（用户不想等），宁可短暂不一致也不阻塞响应。

## 8. 推荐源码阅读顺序

按文件依赖度从低到高：

```
 1. memory/base.py         ← 基础类型，70 行，纯 dataclass/ABC
 2. memory/working.py      ← 最简单实现，108 行，纯内存
 3. memory/episodic.py     ← 第一个 SQLite 实现，215 行
 4. memory/semantic.py     ← 最复杂的 SQL 逻辑，241 行
 5. memory/vector.py       ← ChromaDB 集成，213 行
 6. memory/manager.py      ← 编排层，295 行
```

读的时候注意：
- 每个 `*Memory` 类都实现 `BaseMemory` 接口 (store/retrieve/forget/clear/consolidate)
- `MemoryItem` 是所有层的统一数据格式
- `MemoryContext` 是检索结果的汇总容器
- Manager 的 `record_turn()` 是理解整个写入流的关键

## 9. 推荐扩展方向

按难度递增：

| 扩展 | 难度 | 说明 |
|------|------|------|
| Token 计数 | 低 | WorkingMemory 增加 token 预算追踪，超出时触发强制摘要 |
| 实体关系 | 中 | Semantic 增加实体间关系表 (family/friend/colleague) |
| 分层缓存 | 中 | Episodic 加 LRU 内存缓存，减少 SQL 查询 |
| 多模态记忆 | 中 | Vector 支持图片描述 embed，检索"上次那张截图" |
| 记忆图谱 | 高 | Neo4j 替代 SQLite，实现真正的知识图谱遍历 |
| 主动记忆 | 高 | Agent 主动回顾记忆（非等待用户提问才检索）— "对了，你之前提过..." |

## 10. 简历描述参考

> 设计并实现了 Haven Agent 的四层 Memory 系统：
>
> - **Working Memory** — 基于 deque 的滑动窗口 + LLM 摘要压缩，O(1) 写入，支持 token 预算感知
> - **Episodic Memory** — SQLite 持久化完整对话，hybrid 排序算法 (importance×0.6 + 时间衰减×0.4)，支持 keyword/recent/hybrid 三种检索模式
> - **Semantic Memory** — 实体-事实-历史三层知识图，LLM 异步提取结构化事实，UPSERT + 变更历史追踪，confidence 置信度自动衰减
> - **Vector Memory** — ChromaDB + text-embedding-3-small，余弦相似度检索，三级降级策略 (ImportError → Exception → Silent)
> - **MemoryManager** 统一编排四层生命周期 (record_turn / retrieve / consolidate)，asyncio.create_task 异步模式
