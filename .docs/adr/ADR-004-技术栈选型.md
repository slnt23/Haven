# ADR-004：技术栈选型

> **本文档是架构决策记录（ADR），记录"为什么选择这些技术"。**
> **开发人员请直接阅读 [REQ-002 S10](../requirements/REQ-002-功能需求-系统基础能力.md)，落地清单以 `pyproject.toml` 为准。**

## 一、背景

确定 Agent 定位与基础架构后，为各系统选择具体技术方案。

核心原则：**简单优先，够用就好；为扩展留空间，但不过度设计。**

## 二、决策

| 领域             | 选型                                            | 理由                                             |
| ---------------- | ----------------------------------------------- | ------------------------------------------------ |
| 语言/运行时      | Python 3.14+                                    | AI/LLM 生态成熟；异步友好                          |
| Web 框架         | FastAPI                                         | 高性能异步，自动 OpenAPI，Pydantic 原生集成       |
| 校验 / 配置      | Pydantic v2 / pydantic-settings                 | 与 FastAPI 无缝                                    |
| ORM / 数据库     | SQLAlchemy（异步）+ SQLite（0.0.1）→ PostgreSQL（生产） | 零运维起步，迁移路径清晰                  |
| LLM 接入         | 统一 LLM Gateway（OpenAI 兼容，如 DeepSeek）    | 模型可替换，不绑定厂商                            |
| LLM 编排         | langchain-core / langchain-openai（轻量）       | 结构化输出 + 模型抽象；不引入重型编排             |
| 异步             | asyncio（stdlib）                               | 标准库即可                                        |
| 包管理           | uv                                              | 快速、锁文件可复现（`uv.lock`）                   |
| 日志             | structlog（JSON 结构化）                        | 结构化、便于脱敏与审计                            |
| 定时任务（远期） | APScheduler                                     | 主动关怀/提醒阶段再引入                           |
| 前端形态         | 单页 Web / PWA（面向患者）                      | 具体 UI 框架独立 ADR 决策                         |
| 测试/质量        | pytest + pytest-asyncio；mypy + ruff            | 验收强制（见 REQ-003 NF5）                        |

## 三、不选的技术（及原因）

| 不选                          | 原因                                               |
| ----------------------------- | -------------------------------------------------- |
| 重型编排框架（LangGraph 全量）| 0.0.1 闭环不需复杂编排，工具层按需引入             |
| 分布式任务/缓存（Celery/Redis）| 单进程架构不需要                                    |
| 向量库（ChromaDB/Qdrant）     | 0.0.1 无知识检索，Phase 2 再评估                   |
| 时序库/图库/消息队列/gRPC/Django/K8s | 复杂度远超 MVP 需要                        |

## 四、后果

- 正面：依赖少、启动快、零运维、升级路径明确。
- 风险：SQLite 并发写有上限（MVP 规模无碍）；技术选型是**既定基线**——若引入重型框架或更换核心栈，须新增 ADR 说明理由。
