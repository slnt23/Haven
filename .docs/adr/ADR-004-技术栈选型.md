# ADR-004：技术栈选型

> 状态：提议中
> 日期：2026-08-25
> 依赖：ADR-001, ADR-002, ADR-003

---

## 一、背景

在确定了 Agent 定位和基础能力架构后，需要为每个系统选择具体的技术实现方案。

核心原则：**简单优先，够用就好，为未来扩展留空间但不过度设计。**

---

## 二、决策

### 2.1 编程语言与运行环境

**决策：Python 3.12+**

**理由**：

- AI/LLM 生态最成熟的语言
- LangChain、LangGraph 等框架原生支持
- 团队熟悉度高
- 数据处理和科学计算库丰富

**备选方案**：TypeScript/Node.js（LLM 生态不如 Python 成熟）

### 2.2 核心框架选型

| 组件         | 选型                  | 版本          | 理由                                           |
| ------------ | --------------------- | ------------- | ---------------------------------------------- |
| **LLM 框架** | LangChain + LangGraph | latest stable | 最成熟的 LLM 应用框架，Agent 和 Chain 抽象完善 |
| **Web 框架** | FastAPI               | ≥0.115        | 高性能异步框架，自动生成 OpenAPI 文档          |
| **数据验证** | Pydantic              | v2            | FastAPI 原生集成，类型安全                     |
| **配置管理** | pydantic-settings     | latest        | 与 Pydantic 无缝集成                           |
| **异步支持** | asyncio               | stdlib        | Python 标准库，无需额外依赖                    |
| **包管理**   | uv                    | latest        | 极快的 Python 包管理器                         |

### 2.3 数据存储

| 存储需求                  | 选型                              | 理由                                             |
| ------------------------- | --------------------------------- | ------------------------------------------------ |
| **用户画像 & 结构化数据** | SQLite（MVP）→ PostgreSQL（生产） | SQLite 零配置，适合 MVP；PostgreSQL 适合生产环境 |
| **健康时间线**            | SQLite 时序表                     | 简单场景不需要 InfluxDB/TimescaleDB              |
| **向量存储**              | ChromaDB 或 Qdrant（轻量模式）    | Phase 2 引入，用于知识检索                       |
| **对话历史**              | 内存滑动窗口                      | MVP 阶段不需要持久化全量对话                     |
| **文件存储**              | 本地文件系统                      | MVP 阶段不需要 OSS                               |

**SQLite 的适用性论证**：

- MVP 阶段用户量小（< 1000），SQLite 完全够用
- 零运维成本，开发效率高
- 健康数据量不大（每个用户每天几十条记录）
- 未来迁移到 PostgreSQL 成本低（SQLAlchemy 抽象层）

### 2.4 LLM 选型

| 场景           | 选型                      | 理由                     |
| -------------- | ------------------------- | ------------------------ |
| **对话生成**   | DeepSeek-V3 / GPT-4o-mini | 性价比高，中文能力强     |
| **意图分类**   | DeepSeek-V3 / 小模型      | 低延迟，低成本的分类任务 |
| **结构化提取** | DeepSeek-V3 / GPT-4o-mini | 需要良好的指令遵循能力   |
| **知识问答**   | DeepSeek-V3 + RAG         | 结合知识库提升准确性     |
| **紧急识别**   | 关键词匹配 + 规则         | 零延迟，100% 可靠        |

**设计原则**：

- 能不用 LLM 就不用 LLM（规则、模板、计算优先）
- 能用小模型不用大模型（成本控制）
- LLM 调用统一经过 Gateway 层，方便切换

### 2.5 前端

| 选型       | 理由                                    |
| ---------- | --------------------------------------- |
| **Web UI** | 单页应用，面向患者和家属                |
| **框架**   | React / Vue 3（待定，取决于前端开发者） |
| **PWA**    | 支持推送通知，接近原生体验              |
| **移动端** | 远期考虑 React Native / Flutter         |

### 2.6 定时任务与异步处理

| 组件         | 选型                                          | 理由                      |
| ------------ | --------------------------------------------- | ------------------------- |
| **定时任务** | APScheduler                                   | 轻量级，Python 原生，够用 |
| **消息队列** | 暂无（MVP）                                   | 单进程架构不需要消息队列  |
| **后台任务** | asyncio.create_task / FastAPI BackgroundTasks | 轻量级后台处理            |

### 2.7 日志与监控

| 组件           | 选型               | 理由                       |
| -------------- | ------------------ | -------------------------- |
| **结构化日志** | structlog          | 结构化日志，支持 JSON 输出 |
| **审计日志**   | 自定义 SQLite 存储 | 医疗合规要求               |
| **错误追踪**   | Sentry（可选）     | 生产环境异常监控           |

### 2.8 测试

| 类型         | 工具           | 理由                      |
| ------------ | -------------- | ------------------------- |
| **单元测试** | pytest         | Python 生态标准           |
| **异步测试** | pytest-asyncio | 异步代码测试              |
| **类型检查** | mypy           | 静态类型检查              |
| **代码风格** | ruff           | 极快的 linter + formatter |

### 2.9 部署

| 阶段           | 方案                                   | 理由           |
| -------------- | -------------------------------------- | -------------- |
| **开发**       | 本地运行                               | 零成本         |
| **MVP 演示**   | 单机部署（FastAPI + SQLite）           | 极简部署       |
| **小规模生产** | Docker Compose（FastAPI + PostgreSQL） | 容器化，易维护 |
| **规模化**     | Kubernetes + 云服务                    | 按需扩展       |

## 三、不选的技术（及原因）

| 不选                          | 原因                               |
| ----------------------------- | ---------------------------------- |
| **LangChain 旧版 Agent 框架** | 旧项目遗留，已被 LangGraph 取代    |
| **ChromaDB（MVP 阶段）**      | MVP 不需要向量检索，Phase 2 再引入 |
| **Redis / Memcached**         | 单进程架构不需要外部缓存           |
| **Celery / RabbitMQ**         | 不需要分布式任务队列               |
| **Django**                    | 过重，FastAPI 更适合 API 服务      |
| **gRPC**                      | 单体架构不需要内部 RPC             |
| **Kubernetes（MVP）**         | 过度设计，单机部署即可             |
| **Neo4j / 图数据库**          | 知识图谱的复杂度远超 MVP 阶段需要  |
| **InfluxDB / TimescaleDB**    | 时序数据量不大，SQLite 够用        |

## 五、后果

### 5.1 正面后果

- 依赖极少，项目轻量，启动快
- SQLite 零运维，开发效率高
- 技术栈成熟稳定，社区支持好
- 为未来扩展留了明确的升级路径

### 5.2 风险

- SQLite 在并发写入时有瓶颈（MVP 阶段用户量小，不是问题）
- 单进程架构限制了水平扩展能力（Phase 3 前不需要）
- Python GIL 对 CPU 密集任务有影响（健康数据分析不是 CPU 密集）
