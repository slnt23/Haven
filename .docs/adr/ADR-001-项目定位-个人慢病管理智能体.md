## 一、背景与动机

### 1.1 旧项目的局限

Haven 原定位为"多智能体交互框架"，本质是通用 Agent 框架（CLI/飞书/HTTP 多入口、Planner→Router→Executor、Memory/Skill/Workflow 等通用能力）的封装层。

问题在于：**框架本身不产生用户价值**。用户不会因为有一个"框架"而使用产品，用户需要的是一个能解决具体问题的 Agent。

### 1.2 核心洞察

慢病管理的本质不是"看病"，而是**长期行为改变与风险监控**：

- 医生做的是"关键时刻的决策"
- Agent 做的是"日常时刻的陪伴与管理"

两者互补，而非替代。中国慢病患者基数大、医生资源稀缺，患者在两次门诊之间长期处于"无人管理"状态——这正是 AI Agent 的用武之地。

---

## 二、决策

**Haven 定位为 Personal Chronic Disease Management Agent（个人慢病管理智能体）**：面向患者的、长期陪伴型的 AI 健康管理伙伴。

| 维度     | 主张                                             |
| -------- | ------------------------------------------------ |
| 长期陪伴 | 持续数月乃至数年的健康伙伴关系，而非一次性问答   |
| 状态理解 | 持续追踪健康数据，建立完整健康画像               |
| 风险管理 | 基于趋势提前识别风险，给出保守清晰的干预指引     |
| 安全边界 | 明确不是医疗诊断工具，关键时刻引导线下就医       |

**目标用户**：已确诊慢病（高血压、糖尿病等）患者，40-70 岁；次要用户为患者家属。

**产品边界（不是）**：不是医疗诊断工具、不是在线问诊平台、不是通用 Chatbot、不是资讯聚合器、不是电子病历。

---

## 三、预期效果

- 用户价值：两次门诊之间有一个 7×24 小时的"健康伙伴"，依从性提升、异常早发现。
- 技术价值：架构设计都有明确业务来源，避免"为框架而框架"。
- 商业价值：政策鼓励方向（健康中国 2030），可延伸企业健康 / 保险科技场景。

---

## 四、后果与风险

### 正面后果

- 方向明确，每个功能都有用户价值；可直接面向用户验证、快速迭代。

### 负面风险与缓解

| 风险         | 缓解措施                                                   |
| ------------ | ---------------------------------------------------------- |
| 医疗合规风险 | 明确免责、不做诊断、紧急引导就医（见 REQ 安全兜底）        |
| 数据隐私风险 | 以个人信息保护要求为基线，数据最小化（见 REQ-003/005）     |
| LLM 幻觉风险 | 关键建议限定知识来源；确定性判断不依赖 LLM（见主路线约定） |
| 方向漂移风险 | **一切交付须以 Agent 决策循环形态落地，禁止退化为 CRUD**   |

### 放弃的东西

- 放弃"通用 Agent 框架"定位、多入口泛化架构与 Multi-Agent 编排。
- 旧文档与相关代码仅保留参考价值；`.docs/guide` 等旧方向遗留已清理。
