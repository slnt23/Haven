# ADR-001：项目定位 — 个人慢病管理智能体

> 状态：已接受
> 日期：2026-08-25
> 接受日期：2026-09-01
> 决策者：Haven 项目组

---

## 一、背景与动机

### 1.1 旧项目的局限

Haven 原定位为"多智能体交互框架"，本质是一个通用 Agent 框架（类似 LangChain/LangGraph 的封装层）。其核心价值在于：

- 提供 CLI/Feishu/HTTP 等多入口
- 内置 Planner → Router → Executor 的执行链路
- 提供 Memory、Skill、Workflow 等通用能力

但问题在于：**框架本身不产生用户价值**。用户不会因为有一个"框架"而使用产品，用户需要的是一个能解决具体问题的 Agent。

### 1.2 慢病管理的市场机会

- **用户基数大**：中国慢性病患者超 4 亿，高血压 2.45 亿、糖尿病 1.4 亿
- **管理需求强**：慢病需要长期、持续的管理，而非一次性诊疗
- **医生资源稀缺**：平均每位慢病患者每年仅有 2-3 次门诊机会，其余时间处于"无人管理"状态
- **AI 能力匹配**：LLM 在知识问答、模式识别、个性化建议方面已具备可用能力

### 1.3 核心洞察

慢病管理的本质不是"看病"，而是**长期行为改变与风险监控**。这恰好是 AI Agent 的强项：

- 医生做的是"关键时刻的决策"
- Agent 做的是"日常时刻的陪伴与管理"

两者互补，而非替代。

---

## 二、决策

### 2.1 产品定位

**Haven 重新定位为：Personal Chronic Disease Management Agent（个人慢病管理智能体）**

一个面向患者的、长期陪伴型的 AI 健康管理伙伴，帮助慢病患者管理日常健康、降低疾病风险、提升生活质量。

### 2.2 核心价值主张

| 维度         | 描述                                               |
| ------------ | -------------------------------------------------- |
| **长期陪伴** | 不是一次性问答，而是持续数月甚至数年的健康伙伴关系 |
| **状态理解** | 持续追踪用户的健康数据，建立完整的健康画像         |
| **风险管理** | 基于趋势分析，提前识别风险并给出干预建议           |
| **行为改变** | 通过温和的提醒、鼓励和反馈，帮助用户养成健康习惯   |
| **安全边界** | 明确不是医疗诊断工具，关键时刻引导用户就医         |

### 2.3 目标用户画像

**主要用户**：已确诊慢病（高血压、糖尿病、高血脂、COPD 等）的患者，年龄 40-70 岁

**用户特征**：

- 需要长期服药但依从性差
- 需要定期监测体征但缺乏动力
- 对疾病管理知识了解有限
- 需要情感支持和鼓励
- 可能对技术不太熟悉（需要简单直观的交互）

**次要用户**：患者家属（可代为管理或协同管理）

### 2.4 产品边界（What This Is NOT）

| 不是               | 说明                             |
| ------------------ | -------------------------------- |
| 不是医疗诊断工具   | 不提供诊断，不替代医生           |
| 不是在线问诊平台   | 不连接医生进行实时问诊           |
| 不是通用 Chatbot   | 聚焦慢病管理，不闲聊不泛化       |
| 不是健康资讯聚合器 | 不推送泛健康内容，所有建议个性化 |
| 不是电子病历       | 不做医院级别的病历管理           |

## 三、预期效果

### 3.1 用户价值

- 在医生两次门诊之间，有一个 7×24 小时的"健康伙伴"
- 用药依从性提升、异常指标早发现、健康知识持续积累
- 减少因管理不善导致的急性发作和住院

### 3.2 技术价值

- 所有架构设计都有明确的业务需求来源
- 避免"为框架而框架"的过度设计
- 聚焦真实场景，快速验证和迭代

### 3.3 商业价值

- 慢病管理是政策鼓励的方向（健康中国 2030）
- 患者付费意愿强（直接关系到健康和生活质量）
- 可拓展到企业健康管理、保险科技等 B2B 场景

---

## 四、后果与风险

### 4.1 正面后果

- 产品方向明确，每个功能都有用户价值
- 技术架构服务于产品，避免过度抽象
- 可以直接面向用户验证，快速迭代

### 4.2 负面风险

| 风险         | 缓解措施                                     |
| ------------ | -------------------------------------------- |
| 医疗合规风险 | 明确免责声明，不提供诊断，关键时刻引导就医   |
| 数据隐私风险 | 按目标市场建立合规清单；中国版以个人信息保护要求为基线 |
| 用户留存风险 | 长期陪伴需要真正的价值，不能只是"玩具"       |
| LLM 幻觉风险 | 医疗信息严格限定知识来源，关键建议需人工审核 |
| 用户信任建立 | 初期采用保守策略，逐步建立信任               |

### 4.3 放弃的东西

- 放弃了"通用 Agent 框架"的定位
- 放弃了多入口（CLI/Feishu/Daemon）的泛化架构
- 放弃了 Multi-Agent 协作的复杂编排
- 所有旧文档和相关代码仅保留参考价值
