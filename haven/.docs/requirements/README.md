## 一、产品本质：我们要做一个 Agent

Haven 是一个 **Personal Chronic Disease Management Agent（个人慢病管理智能体）**，代号"健健"。

### 1.1 Agent ≠ Web 应用 + Chatbot

| 特征     | 传统 Web 应用        | Agent                  |
| -------- | -------------------- | ---------------------- |
| 交互模式 | 请求-响应（被动）    | 感知-决策-行动（主动） |
| 状态管理 | 无状态或简单 Session | 持续记忆（短期+长期）  |
| 决策方式 | 固定逻辑分支         | 上下文感知的多步推理   |
| 工具使用 | 无                   | 自主选择调用工具       |
| 主动性   | 等待用户操作         | 可主动追问、关怀       |

**Haven 的 Agent 不是"能聊天的健康记录本"，而是一个能主动思考、决策、行动的智能体。**

### 1.2 Agent 决策循环（唯一实现骨架）

```
用户输入
   │
   ▼
┌──────────────────────────────────────────────┐
│ 1.感知 Perceive  解析输入、识别意图与健康数据  │
└──────────────────────┬───────────────────────┘
                       ▼
┌──────────────────────────────────────────────┐
│ 2.思考 Think       检索用户画像/近期数据/知识  │
└──────────────────────┬───────────────────────┘
                       ▼
┌──────────────────────────────────────────────┐
│ 3.决策 Decide      追问？记录？分析？警告？    │
└──────────────────────┬───────────────────────┘
                       ▼
┌──────────────────────────────────────────────┐
│ 4.行动 Act         执行动作、生成回复、存储    │
└──────────────────────┬───────────────────────┘
                       ▼
┌──────────────────────────────────────────────┐
│ 5.记忆 Remember    更新画像/时间线/会话状态    │
└──────────────────────────────────────────────┘
```

> 支撑实现见 [REQ-002 S9](REQ-002-功能需求-系统基础能力.md)：S9 是项目的中枢，S1/S8/S6 等全部服务于这个循环。

## 二、★ 开发主路线（硬目标）

> 这一节是方向校准，任何偏离都算需求未完成。**宁可少做一个功能，也不要把它做成一棵没有 Agent 的 CRUD 树。**

### 2.1 目标形态

0.0.1（以及其后每个版本）交付的**每一条能力，都必须以"Agent 决策循环"的形态存在**：

1. 收到输入先**感知**（理解意图，而非简单关键词）；
2. **思考**时检索相关记忆与知识形成上下文（用户是谁？近期数据如何？）；
3. **决策**后可多步行动（追问 → 确认 → 记录 → 总结）；
4. **行动**执行并产出回复；
5. 每轮结束**记忆**更新。

**禁止形态**：`路由到 CRUD 端点 → 把结果塞进一句话` 的"chat 门面"。判断标准见 2.3。

### 2.2 0.0.1 的 Agent 闭环基线（横切硬性要求）

即使 0.0.1 只交付高血压一条竖切，也必须具备以下最小机件（与 [TRACEABILITY](TRACEABILITY.md) 的 11 条交付项互为表里，每条交付项都要在它们之上跑通）：

| # | 机件 | 落地要求 | 参考 |
| - | ---- | -------- | ---- |
| 1 | 会话级状态机 | 按用户/会话隔离；**禁止模块级全局单例共享状态** | REQ-002 S8.4 |
| 2 | 记忆注入上下文 | "思考"前必须读取该用户画像 + 近期体征，注入决策上下文 | REQ-002 S9.2 / S1.6 |
| 3 | 多轮确认闭环 | 二次确认、建档引导等必须是"可继续"的对话状态流（用户回"确认"能接上），不能一锤子 | REQ-002 S9.6 |
| 4 | 安全状态按用户隔离 | 紧急/降级状态只作用于当前用户；判定走版本化安全规则 | REQ-002 S6.1 / S9.9 |
| 5 | LLM 降级矩阵 | LLM 不可用时：手工录入、规则校验、趋势计算不中断；DB 不可用不得谎报成功 | REQ-002 S9.9 / REQ-003 NF2 |
| 6 | 流式输出 | 回复走 SSE 逐 token 输出 | REQ-002 S5.1 / S9.7 |

> **关于 1 与 4 的"按用户隔离"**：0.0.1 的实现形态是**单租户 —— 一个部署 = 一个人**
> （[ADR-006](../adr/ADR-006-单租户身份模型.md)）。`user_id` 隔离机制原样保留
> （`REQ-005` §4.3 继续满足），只是服务集合大小为 1：隔离的对象是"这一个用户
> vs 其余任何人"。**禁止模块级全局单例共享状态**这一条不受单租户影响，仍然照旧。

### 2.3 偏离信号（自查清单）

实现或评审时，命中以下任一信号 = 正在偏离主路线，须改回：

- [ ] 交互只是"意图→调一个数据读写函数→文案润色"，没有读用户画像/近期记录；
- [ ] 异常二次确认发出后，用户回复"确认"却续不上（没有对话状态）；
- [ ] 会话或安全状态是模块级全局变量（所有用户共享一个状态）；
- [ ] 功能以"孤立端点"存在，而不承载在 Agent 的一次决策循环里；
- [ ] 相同的"记录"行为，表单路径与对话路径是两套实现且互不相通；
- [ ] 新增能力没有回答"感知到什么、想起什么、决定什么、做什么、记住什么"。

## 七、开发约定

### 7.1 Agent 行为准则

每条能力实现必须能回答：**感知**到（意图/数据）→ **想起**（相关记忆）→ **决定**（下一步）→ **做**（执行+回复）→ **记住**（更新状态）。只实现了增删改查，不算完成。

### 7.2 确定性优先

- 能用规则和计算解决，不用 LLM。
- 数据校验、趋势计算、异常检测 → 确定性代码。
- 意图理解、回复生成、多步推理 → LLM。
- 安全判断 → 规则 + 安全状态机，**不依赖 LLM**。

### 7.3 安全边界

- 所有回复必须过安全过滤器。
- 紧急情况触发安全状态机，保守引导线下就医；否定句、转述、边界体征不得仅凭单关键词判为确定事件。
- 不诊断、不替代医生、不给个性化用药建议。
- 医学建议附带免责声明；审计与日志走最小化原则。
