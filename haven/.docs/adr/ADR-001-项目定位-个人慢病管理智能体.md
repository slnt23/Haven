# ADR-001：项目定位 — 个人慢病管理智能体

- **Status**: Accepted (2026-09-01)
- **Deciders**: Haven 项目组
- **Date**: 2026-08-25

## Context

Haven 原定位为"多智能体交互框架"——CLI/飞书/HTTP 多入口、Planner→Router→Executor 的通用 Agent 框架封装。问题在于：框架本身不产生用户价值，用户需要的是一个能解决具体问题的 Agent。

慢病管理的本质不是"看病"，而是**长期行为改变与风险监控**。医生做"关键时刻的决策"，Agent 做"日常时刻的陪伴与管理"。中国慢病患者基数大、医生资源稀缺，患者在两次门诊之间长期处于"无人管理"状态——这正是 AI Agent 的用武之地。

## Decision Drivers

- 从通用框架转向有明确用户价值的垂直场景
- 长期陪伴 vs 一次性问答
- 安全边界：明确不做医疗诊断

## Considered Options

1. **保持通用多智能体框架**：技术通用性强，但缺乏用户价值锚点，容易"为框架而框架"。Good, because 可复用；Bad, because 不产生用户价值。否决。
2. **个人慢病管理智能体（采纳）**：面向已确诊慢病患者（40-70 岁）的长期陪伴型 AI 健康管理伙伴。

## Decision Outcome

**Chosen option: 个人慢病管理智能体**，聚焦长期陪伴、状态理解、风险管理，明确不是医疗诊断工具。

| 维度 | 主张 |
|------|------|
| 长期陪伴 | 持续数月乃至数年的健康伙伴关系 |
| 状态理解 | 持续追踪健康数据，建立完整健康画像 |
| 风险管理 | 基于趋势提前识别风险，给出保守清晰的干预指引 |
| 安全边界 | 明确不是医疗诊断工具，关键时刻引导线下就医 |

**目标用户**：已确诊慢病（高血压、糖尿病等）患者，40-70 岁；次要用户为患者家属。

**产品边界（不是）**：不是医疗诊断工具、在线问诊平台、通用 Chatbot、资讯聚合器、电子病历。

## Consequences

**Good:**
- 方向明确，每个功能都有用户价值
- 可直接面向用户验证、快速迭代
- 架构设计有明确业务来源，避免"为框架而框架"

**Bad:**
- 医疗合规风险：通过明确免责、不做诊断、紧急引导就医缓解
- 数据隐私风险：以个人信息保护要求为基线，数据最小化
- LLM 幻觉风险：关键建议限定知识来源，确定性判断不依赖 LLM
- 方向漂移风险：一切交付须以 Agent 决策循环形态落地，禁止退化为 CRUD

**Neutral:**
- 放弃通用 Agent 框架定位、多入口泛化架构与 Multi-Agent 编排
