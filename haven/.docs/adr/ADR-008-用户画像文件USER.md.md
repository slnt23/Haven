# ADR-008：用户画像文件 USER.md

- **Status**: Proposed (2026-10-05)
- **Deciders**: Haven 项目组
- **Date**: 2026-10-05
- **Related ADRs**:

  - [ADR-002](./ADR-002-核心能力定义.md)：本决策服务于 C1 健康画像管理、C7 个性化、C8 情感支持陪伴（补充）
  - [ADR-003](./ADR-003-基础能力架构.md)：本决策是 S1 记忆系统中「用户画像」的人类可读表达（补充）

## Context

Haven 当前的用户数据存储在两个层面：

1. **结构化数据库**（`health_profiles`、`disease_records`、`blood_pressure_records` 等）：存储可结构化的健康指标——性别、出生日期、身高体重、疾病诊断、血压数值。这些数据是「硬事实」，用于确定性计算（趋势分析、风险评估）。
2. **对话记忆**（MDA 托管运行时的持久线程 + 记忆注入）：存储会话上下文，但这是面向模型的 token 注入，而非面向人类阅读的画像总结。

缺失的是**第三层**：一个随着对话持续演进的、人类可读的「用户画像」文件。Agent 在长期陪伴中会积累大量关于用户的「软信息」——比如：

- 用户提到家里有几口人、谁在帮忙照顾
- 用户偏好的沟通风格（简洁直接 vs 温和共情）
- 用户的生活节奏（几点起床、什么时候方便量血压）
- 用户对疾病的态度（积极管理 vs 回避焦虑）
- 用户的饮食偏好、运动习惯、日常困扰
- 用户反复提及的担忧或目标

这些信息散落在多轮对话里，目前没有被系统地总结和沉淀。数据库里的结构化字段承载不了这些，而对话记忆的 token 窗口有限且不面向人读。

**USER.md 的定位**：它是 Agent 对用户不断加深理解的「笔记」。每一次有意义的交互后，Agent 可以将新了解到的用户信息总结并追加/更新到 USER.md 中。这份文件：

- **人类可读**：用户本人、家属、开发者都可以直接打开阅读
- **持续演进**：不是一次性填写，而是随对话逐步丰富
- **服务于个性化**：Agent 可以在每次对话开始时注入 USER.md 的摘要，实现更精准的个性化交互

## Decision Drivers

- 需要一个承载「软信息」的载体，补充结构化数据库的不足
- 文件应人类可读，便于用户查看、家属了解、开发者调试
- 信息应随对话自动积累，而非要求用户一次性填写
- 须有清晰的信息结构，避免变成杂乱无章的日志
- 隐私安全：USER.md 包含用户个人信息，须与数据库同等级别保护
- 与现有数据库画像不重复：USER.md 不替代 `HealthProfile`，而是互补

## Considered Options

### 方案 A：扩展数据库字段（如新增 `user_preferences` 表）

在数据库中新增自由文本字段或键值对表，存储偏好、习惯等软信息。

**Good, because...**

- 数据结构化，可查询
- 与现有数据层一致，复用 ORM 和审计

**Bad, because...**

- 自由文本在关系型数据库中不便于人类直接阅读
- 每次新增信息类型都需要改 schema，不够灵活
- 无法直接给用户或家属查看——需要额外开发 UI
- 与「人类可读、随时可看」的目标矛盾
- **否决**

### 方案 B：纯 LLM 记忆（仅依赖对话线程的 token 注入）

不额外存储，完全依赖 MDA 托管运行时的持久线程和记忆注入来传递用户画像信息。

**Good, because...**

- 零额外开发
- LLM 自动从对话历史中提取相关信息

**Bad, because...**

- Token 窗口有限，远期对话的信息会被截断
- 信息不持久化：重新部署或线程重置后画像丢失
- 不可被人类直接查阅
- 无法做跨会话的画像一致性管理
- **否决**

### 方案 C：USER.md 文件（采纳）

在用户数据目录下维护一个 `USER.md` 文件，Agent 在每次有价值的交互后，自动总结并更新该文件。文件包含清晰的个人信息结构，人机皆可读。

**Good, because...**

- **人类可读**：用户、家属、开发者均可直接打开阅读，无需任何工具
- **灵活演进**：Markdown 格式天然支持渐进式补充，不需要改 schema
- **服务于个性化**：Agent 可以在对话开始时读取 USER.md（或摘要），实现精准个性化
- **版本可追溯**：作为文件纳入版本管理或备份，画像演进历史可查
- **与数据库互补**：数据库管「硬事实」，USER.md 管「软画像」，互不替代
- **结构清晰**：定义好章节模板后，信息不会散乱

**Bad, because...**

- 文件 I/O 比数据库查询慢——但 USER.md 通常只在会话开始时读取一次，影响可忽略
- 并发写入风险——单租户部署下不存在并发，且 Agent 是单线程对话
- LLM 生成的总结质量不稳定——需要通过 prompt 约束输出格式，并做基本校验
- 文件可能被用户误编辑——可视为 feature：用户有权修正 Agent 对自己的理解
- 隐私敏感——文件内容须与数据库同等级别保护（本地加密或依赖部署环境隔离）

### 方案 D：USER.md + 数据库索引（远期增强）

在方案 C 基础上，数据库维护一个轻量的「画像摘要索引」（如关键标签列表），加速结构化查询。USER.md 仍是主存储，索引只是缓存。

**Good, because...**

- 可支撑「按标签检索用户特征」等高级功能

**Bad, because...**

- 增加同步复杂度
- 0.0.x 阶段不需要
- **远期考虑，本次不采纳**

## Decision Outcome

**Chosen option: 方案 C — USER.md 文件**，作为结构化数据库之外的人类可读用户画像载体。

### USER.md 的结构设计

USER.md 按以下章节组织，Agent 在对话中获取新信息时，更新对应章节：

```markdown
# 用户画像 — {用户称呼}

> 本文件由 Haven Agent 在日常交流中自动总结生成，持续更新。
> 最后更新：{日期}

## 基本信息

- 称呼：{nickname}
- 性别：{gender}
- 出生年份：{birth_year}
- 身高/体重：{height}cm / {weight}kg
- 所在地/时区：{location}

## 健康状况

- 确诊疾病：{disease list with diagnosis dates}
- 当前关注：{active health concerns}
- 用药情况：{current medications}
- 过敏信息：{allergies}

## 生活习惯

- 饮食偏好：{dietary preferences / restrictions}
- 作息规律：{sleep/wake patterns}
- 运动习惯：{exercise habits / limitations}
- 烟酒情况：{smoking / drinking}

## 沟通偏好

- 语言风格：{formal / casual / concise}
- 称呼偏好：{how user likes to be addressed}
- 沟通频率：{preferred interaction frequency}
- 特别注意事项：{communication notes}

## 家庭与社交

- 家庭成员：{family members / living situation}
- 主要照护者：{primary caregiver}
- 社交情况：{social context}

## 心理与情绪

- 对疾病的态度：{attitude towards condition}
- 主要担忧：{key concerns}
- 动力来源：{motivations}
- 情绪特点：{emotional patterns}

## 目标与偏好

- 健康目标：{health goals}
- 生活方式目标：{lifestyle goals}
- 对 Haven 的期望：{expectations from the agent}

## 交互记录摘要

- 首次对话：{date}
- 累计交互次数：{count}
- 近期主题：{recent topics}
- 重要里程碑：{key milestones}
```

### 更新机制

1. **触发时机**：每次对话结束后（或对话中 Agent 识别到有意义的用户信息时），Agent 评估是否需要更新 USER.md
2. **更新方式**：Agent 读取当前 USER.md → 对比新获取的信息 → 生成更新后的完整文件 → 写入
3. **更新粒度**：追加新信息、修正过时信息、补充细节——不做全量重写
4. **防抖策略**：同一信息在短时间内不重复更新；仅在信息有实质变化时更新
5. **用户可控**：用户可以直接编辑 USER.md 修正 Agent 的理解；用户可以说「忘记我提到过的 XX」触发对应条目清除

### 存储位置

`{HAVEN_DATA_DIR}/USER.md`，其中 `HAVEN_DATA_DIR` 默认为 `.data/`（与 SQLite 数据库同目录）。单租户部署下，一个实例只有一个 USER.md。

### 隐私与安全

- USER.md 与数据库文件同目录，享受同等级别的文件系统权限保护
- 包含在「删除我的数据」（C11 安全兜底）的范围之内——用户请求数据删除时，USER.md 一并清除
- 不包含原始对话记录——只包含总结提炼后的画像信息

### 与现有系统的关系

| 现有系统                  | 与 USER.md 的关系                                                                   |
| ------------------------- | ----------------------------------------------------------------------------------- |
| `HealthProfile`（数据库） | USER.md 的「基本信息」「健康状况」从数据库同步骨架，Agent 对话补充细节              |
| `DiseaseRecord`（数据库） | 同「健康状况」                                                                      |
| S1 记忆系统               | USER.md 作为记忆注入的**人类可读源**之一；每次对话开始时可将 USER.md 摘要注入上下文 |
| S7 个性化系统             | USER.md 是「沟通偏好」「心理与情绪」等个性化维度的数据源                            |
| ADR-006 单租户身份        | 一个 `HAVEN_OWNER_ID` 对应一个 USER.md                                              |
| C11 安全兜底 / 数据删除   | `delete_my_data` 须同步删除 USER.md                                                 |

## Consequences

**Good:**

- 填补了「结构化数据库」与「LLM 对话记忆」之间的空白——有了人类可读的持久画像
- Agent 个性化能力有明确的数据来源：每次对话前注入 USER.md，交互更贴合用户
- 用户和家属可以直接查看 Agent 对自己的理解，增强信任与透明度
- 灵活演进：Markdown 格式天然支持渐进补充，新增章节无需改代码
- 画像历史可通过文件版本追溯（git 或文件备份）
- 用户可直接编辑文件修正 Agent 的理解，降低「AI 理解偏差」的风险

**Bad:**

- LLM 生成内容质量不可控：需要良好的 prompt 设计约束总结格式，且需对输出做基本校验（章节完整性、无越权内容）
- 文件可能膨胀：长期运行后 USER.md 可能变得很长。需要定期压缩/摘要旧内容，或将过时信息归档
- 增加了数据删除的范围：`delete_my_data` 需要额外处理 USER.md 的清除
- 文件 I/O 比数据库查询慢：大量对话场景下需评估性能影响

**Neutral:**

- 与数据库画像的关系需要明确：USER.md 是数据库的「人类可读补充」，不是替代。两者之间的同步策略（谁为准、何时同步）需在实现阶段细化
- LLM 更新文件的操作本身也是一种工具调用，需要在 Agent 的工具集中增加 `update_user_md` 工具
