# ADR-006：单租户身份模型 —— 一个部署 = 一个人

> **本文档是架构决策记录（ADR），记录"为什么把身份钉在配置里"。**
> **开发人员请直接阅读 [requirements/](../requirements/README.md)，那里有你需要实现的内容。**
>
> 状态：已接受
> 日期：2026-09-10
> 依赖：ADR-001（个人慢病管理智能体）、ADR-005（0.0.1 范围收敛）

---

## 一、背景与动机

### 1.1 身份原本完全交给平台注入

全项目的身份只有一个来源：`storage/database.py` 的 `caller_user_id()`，它读
MDA 运行时注入的 `runtime.identity["user"]["id"]`。这个值由平台决定，作者侧
无法控制，且**每种运行方式给出的东西都不一样、都不是"人"**：

| 运行方式 | 注入的 id |
| -------- | --------- |
| 本机 `mda dev` | 合成服务主体 `mda:local-dev` |
| LangGraph Studio | `langgraph-studio-user`（`kind: service`） |
| 部署后持 LangSmith workspace key | `langsmith:user:<key 属主 id>`（`kind: service`） |
| 以上都不成立（例如绕开 `mda` 直接用 LangGraph CLI 指向构建产物） | **`identity is None`** |

### 1.2 由此产生的三个问题

1. **数据会分家**：同一个人在本地 dev 与云端部署是两个不同的 `user_id`，
   档案、血压、建档进度互不可见 —— 而"长期陪伴"（ADR-001）恰恰要求同一份数据。
2. **本机所有调用者共用一个身份**：`mda:local-dev` 是机器级的，不是人的。
3. **身份缺失时全线拒绝**：`identity is None` 时 10 个工具 + `/cancel` 一律返回
   `NO_IDENTITY_REPLY`，一条用户路径都跑不通（0.0.1 实际发生过：本地库文件从未
   被创建，所有调用都卡在身份闸门上）。

### 1.3 产品本身是单人的

`ADR-001` 定位「个人慢病管理智能体」，`ADR-005` 明确「家庭协同和多患者管理」不在
0.0.1 内，`REQ-003` NF3.3 写明「0.0.1 为本地单人演示」。**代码里却没有任何一处
体现"这是一个人的东西"** —— 身份是产品的第一属性，不该由部署环境临时决定。

---

## 二、决策

**单租户：一个部署 = 一个人。本人 id 由配置 `HAVEN_OWNER_ID` 授予，运行时不参与授予。**

| 运行时身份 | 处理 |
| ---------- | ---- |
| 不存在 | 用配置的 `owner_id` |
| `kind == "service"`（本地 dev / Studio / channel / schedule / LangSmith-key 主体） | 用配置的 `owner_id` —— 服务主体不是"人"，不参与校验 |
| `kind == "person"` 且 `id == owner_id` | 用 `owner_id` |
| `kind == "person"` 且 `id != owner_id` | **拒绝**（记一条 WARNING 日志，含期望/实际 id） |

职责分离：

- `identity.py` 回答**"能不能进"**（准入认证，当前为 LangSmith workspace API key）；
- `HAVEN_OWNER_ID` 回答**"进来的是谁"**（本人身份）。

### 关键性质

- **`user_id` 隔离机制一条不改**：6 张表的 `user_id` 列、~25 处
  `user_id == uid` 过滤全部保留（`REQ-005` §4.3）。它从"多用户隔离"退化为
  "单一命名空间"，语义仍然正确，将来加人无需改表。
- **"非本人拒绝"是纵深防御，不是主闸门**：LangSmith-key 模式下没有"人"的身份
  （所有调用者都是 `service`），这条校验**永远不会触发**；真正拦住外人的是
  `identity.py` 的认证。它的价值在将来接 Supabase（每人一个 `person` 身份）时兑现。

## 三、备选方案与取舍

| 方案 | 取舍 |
| ---- | ---- |
| **A. 不动，继续用平台注入的身份** | 零改动，但 1.2 的三个问题全部保留：数据分家、本机身份共享、身份缺失即全线拒绝。**否决** |
| **B. 删掉 `identity.py`，彻底关认证** | 身份永远为 `None`，端点完全开放，健康数据无任何准入控制。**否决** |
| **C.（采纳）身份由 `HAVEN_OWNER_ID` 配置授予** | 本机 dev 与云端部署是同一个人；身份不再依赖平台行为。代价：多一个配置项，且本地与云端**必须配同一个值**（写进 README 部署注意） |
| **D. MDA 原生 `auth="backend"` + 常量 `x-mda-user-id`** | 平台支持的"固定身份"路径，但要求自建网关转发 `x-mda-ingress-secret`，且本地 `mda dev` 不带这些头会直接 401 —— 本地跑不起来。**本次不采用**；将来做硬化部署可作为第二道闸门叠加 |

另：**MDA 记忆（`memory.py`）这条路依然封死** —— 它是部署级共享的一个
`/memories/agent/` 树，一个部署里所有调用者读写同一棵，健康数据绝不写入。
本决策不改变这一点。

---

## 四、后果

### 正面

- 同一个人在本机 dev、Studio、云端部署看到**同一份数据**，"长期陪伴"成立。
- 身份不再依赖平台的注入行为：平台换了主体命名、或某条路径不注入身份，
  业务都不受影响。
- 将来给家人用 = **再部署一个实例**（不同 `HAVEN_OWNER_ID` + 不同库），代码零改动。

### 负面与风险

- 多一个必须正确的配置项：`HAVEN_OWNER_ID` 本机与云端配得不一致，就会出现
  两份"同一个人的数据"。已写进 README「健健部署注意」。
- 配错时会把自己拒之门外（日志里有期望/实际 id）。**这是有意的**：拒绝方向比
  放行方向安全，且可自愈（改配置即可）。
- 单租户不等于多用户能力保留：真要"一个部署服务多人"，需要重做身份模型
  （Supabase 身份 + 白名单），不在 0.0.1 内。

### 对需求文档的影响

- `REQ-002` S1.8 记忆隔离、`REQ-005` §4.3 数据访问控制**不变**：没有被违反，
  只是服务集合大小为 1。
- `REQ-003` NF3.3 / NF3.4 与 `TRACEABILITY` B1 / B4 加注解说明"按用户隔离"
  在单租户下的实际含义。
