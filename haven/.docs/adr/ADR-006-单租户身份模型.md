# ADR-006：单租户身份模型

- **Status**: Accepted (2026-09-10)
- **Deciders**: Haven 项目组
- **Date**: 2026-09-10
- **Depends on**: ADR-001, ADR-005

## Context

全项目的身份来源是 `caller_user_id()`，读 MDA 运行时注入的 `runtime.identity["user"]["id"]`。每种运行方式给出的身份都不同，且都不是"人"：

| 运行方式 | 注入的 id |
|----------|-----------|
| 本机 `mda dev` | 合成服务主体 `mda:local-dev` |
| LangGraph Studio | `langgraph-studio-user`（`kind: service`） |
| 部署后持 LangSmith workspace key | `langsmith:user:<key 属主 id>`（`kind: service`） |
| 绕开 `mda` 直接用 LangGraph CLI | **`identity is None`** |

由此产生三个问题：

1. **数据分家**：同一个人在本地 dev 与云端部署是两个不同的 `user_id`，档案互不可见
2. **本机所有调用者共用一个身份**：`mda:local-dev` 是机器级的
3. **身份缺失时全线拒绝**：`identity is None` 时所有调用返回 `NO_IDENTITY_REPLY`

产品本身是单人的（ADR-001 定位「个人慢病管理智能体」，ADR-005 明确家庭协同不在 0.0.1 内），代码里却没有体现——身份不应由部署环境临时决定。

## Decision Drivers

- 同一个人的数据在本地 dev 与云端部署必须一致（"长期陪伴"的基础）
- 身份不应依赖平台的注入行为
- 保持 `user_id` 隔离机制不变（为将来多用户留余地）

## Considered Options

| 方案 | Good, because... | Bad, because... |
|------|-------------------|------------------|
| **A. 不动，继续用平台注入的身份** | 零改动 | 数据分家、本机身份共享、身份缺失即拒绝。**否决** |
| **B. 删掉 `identity.py`，彻底关认证** | 最简单 | 端点完全开放，健康数据无准入控制。**否决** |
| **C.（采纳）身份由 `HAVEN_OWNER_ID` 配置授予** | dev 与云端是同一人；身份不依赖平台行为 | 多一个必须正确的配置项 |
| **D. MDA 原生 `auth="backend"` + `x-mda-user-id`** | 平台支持的固定身份路径 | 本地 `mda dev` 不带头会直接 401。**本次不采用**，将来硬化部署可叠加 |
| **E. 用户在对话里自报 `user_id`** | 省掉配置 | 自报 id 不是认证；打错字 = 数据静默分家。**否决** |

## Decision Outcome

**Chosen option: 单租户 —— 一个部署 = 一个人。本人 id 由配置 `HAVEN_OWNER_ID` 授予。**

| 运行时身份 | 处理 |
|-----------|------|
| 不存在 | 用配置的 `owner_id` |
| `kind == "service"` | 用配置的 `owner_id`（服务主体不是"人"） |
| `kind == "person"` 且 `id == owner_id` | 用 `owner_id` |
| `kind == "person"` 且 `id != owner_id` | **拒绝**（记 WARNING 日志） |

职责分离：`identity.py` 回答"能不能进"（准入认证）；`HAVEN_OWNER_ID` 回答"进来的是谁"（本人身份）。

**关键性质**：

- `user_id` 隔离机制一条不改：6 张表的 `user_id` 列、~25 处过滤全部保留，语义从"多用户隔离"退化为"单一命名空间"，将来加人无需改表
- "非本人拒绝"是纵深防御，不是主闸门：LangSmith-key 模式下不会触发；将来接 Supabase 时兑现

> **称呼 ≠ 身份**。用户想在对话里被叫名字，那是 `HealthProfile.nickname`——档案数据，可跳过、可修改。

## Consequences

**Good:**
- 同一个人在本机 dev、Studio、云端部署看到同一份数据，"长期陪伴"成立
- 身份不再依赖平台的注入行为
- 将来给家人用 = 再部署一个实例（不同 `HAVEN_OWNER_ID` + 不同库），代码零改动

**Bad:**
- 多一个必须正确的配置项：本机与云端配得不一致会出现两份"同一个人的数据"
- 配错时会把自己拒之门外（日志里有期望/实际 id）。拒绝方向比放行安全，可自愈
- 单租户 ≠ 多用户能力保留：真要"一个部署服务多人"需重做身份模型，不在 0.0.1 内

**Neutral:**
- REQ-002 S1.8 记忆隔离、REQ-005 §4.3 数据访问控制不变，只是服务集合大小为 1
