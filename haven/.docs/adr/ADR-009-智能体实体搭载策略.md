# ADR-009：智能体实体搭载策略 — 从"专属设备"到"融入用户生活全场景"

- **Status**: Proposed (2026-10-23)
- **Deciders**: Haven 项目组
- **Related ADRs**:
  - [ADR-007](./ADR-007-语音交互与实体部署.md)：本决策是对 ADR-007 设备策略的扩展——ADR-007 确立了自建语音终端的长期方向，本 ADR 在此基础上将视野从"单一终端"扩展为"用户生活全场景的设备生态"（补充/扩展）
  - [ADR-002](./ADR-002-核心能力定义.md)：C10 主动关怀、C11 安全兜底需要多设备协同才能完整落地（依赖）
  - [ADR-003](./ADR-003-基础能力架构.md)：S5 通信系统和 S9 Agent 核心引擎需具备设备无关的抽象能力（依赖）

## Context

ADR-007 确立了 Haven 从纯软件走向软硬一体的长期方向，并选定"自建语音交互终端"作为主方案。但这只回答了"我们要做什么设备"，尚未回答一个更根本的问题：

**智能体应该搭载在什么设备上，才能最自然地融入用户的生活？**

目标用户群体（40-70 岁慢病患者）的日常生活场景远比"坐在家里对着一个语音终端"丰富得多。他们出门散步、看病、买菜、串门——在这些移动场景中，一个固定在客厅的设备无法提供陪伴。更重要的是，用户的生活场景中已经存在大量"天然搭载点"：

- **随身必备的设备**：智能手机几乎是每个人的"体外器官"，智能手表/手环也被广泛接受
- **不得不依赖的设备**：使用轮椅、拐杖、助行器的用户，这些辅具就是他们身体的一部分，每天接触时间可能超过任何电子设备
- **用户偏爱的设备**：有些老人就喜欢看电视、有些习惯用平板、有些只用老人机——强迫他们接受一个新设备，本质上是在制造接入障碍

此外，即使某些设备本身不具备搭载 Agent 的条件（如一副普通拐杖、一台机械轮椅），但如果能与之**联动**——例如拐杖上的传感器检测到步态异常，轮椅的移动数据反映活动量下降——这些"沉默的设备"就能成为 Agent 感知用户状态的触角。

因此，Haven 需要一个**以用户生活场景为中心、而非以某个特定设备为中心**的实体搭载策略。

## Decision Drivers

- **用户偏好优先**：Agent 应适应用户偏好的设备形态，而非要求用户适应 Agent 选定的设备
- **随身性**：Agent 的"陪伴"价值在用户移动时不应中断——需要考虑移动场景的搭载方案
- **辅助设备的特殊性**：轮椅、拐杖、助听器等辅助设备是用户"不得不依赖"的身体延伸，搭载或联动价值极高
- **零门槛原则**：不强迫用户购买或学习使用新硬件，优先利用用户已有的设备
- **多设备协同**：不同设备承担不同角色（感知/交互/告警/展示），Agent 在设备间无缝流转
- **不适合搭载 ≠ 不可联动**：即使某类设备无法运行 Agent 逻辑，也应考虑数据联动、信号互通
- **核心引擎设备无关**：S9 Agent 核心引擎的决策逻辑不绑定任何具体设备形态

## Considered Options

### 方案 A：单一终端策略 — 只推自建语音终端

沿用 ADR-007 的结论，集中资源打造一款 Haven 自有语音终端，所有交互都通过这台设备完成。

**Good, because...**

- 研发资源集中，不需要适配多种设备
- 软硬件一体，体验可控，隐私链路完整
- ADR-007 已有详细的技术路线图

**Bad, because...**

- 用户需要购买新设备、学习使用新设备——对老年用户是显著门槛
- 固定在家的设备无法覆盖移动场景（出门、看病、散步）
- 忽视了用户已经拥有且习惯使用的设备（手机、手表、电视）
- 忽视了辅助设备（轮椅、拐杖）作为天然搭载点的价值
- 当用户偏爱的设备不是语音终端时，Agent 的"陪伴"无法触达用户
- **单点依赖**：设备故障 = Agent 失联

### 方案 B：手机 App 为主策略

以智能手机 App 为主要交互终端，语音终端仅作为可选配件。

**Good, because...**

- 智能手机几乎人人都有，零硬件成本
- 移动场景全覆盖
- 开发生态成熟

**Bad, because...**

- ADR-007 已分析：手机不是"环境设备"，无法做到真正的"始终在线"和"唤醒即聊"
- 40-70 岁群体中仍有相当比例不熟悉智能手机
- App 后台保活受限，主动巡检不可靠
- 屏幕交互对视力不佳的老人不友好

### 方案 C：设备生态策略 — 核心引擎设备无关，多设备分层搭载（采纳）

将"Agent 应该搭载在什么设备上"的问题倒过来问：**用户的生活场景中已经有了哪些设备？Agent 如何融入这些设备？**

核心原则：

1. **Agent 核心引擎（S9）保持设备无关**：决策逻辑只处理"感知→思考→决策→行动"循环，不关心输入来自哪个设备、输出发往哪个设备
2. **每类设备通过适配层接入**：设备负责输入/输出（麦克风、屏幕、扬声器、传感器），适配层负责将设备信号翻译为 Agent 可理解的事件
3. **设备分三层，按用户实际情况组合**：

**第一层：随身层（Always-On）**

用户始终携带、或不得不依赖的设备。Agent 应优先通过这一层接入用户。

| 设备类型                  | 搭载可行性         | 交互模态         | 典型场景                     |
| ------------------------- | ------------------ | ---------------- | ---------------------------- |
| 智能手机                  | ★★★★★ 全功能搭载   | 语音+触屏+通知   | 通用移动场景，App/小程序     |
| 智能手表/手环             | ★★★ 轻量搭载       | 语音+振动+心率   | 被动健康监测、紧急告警       |
| 智能拐杖/助行器           | ★★★ 感知为主       | 语音播报+传感器  | 步态监测、跌倒检测、一键求助 |
| 智能轮椅                  | ★★★★ 可搭载        | 语音+屏幕+传感器 | 活动量追踪、久坐提醒、导航   |
| 智能眼镜/助听器           | ★★ 轻量交互        | 骨传导语音       | 轻量通知、关键信息播报       |
| 传统辅具（普通拐杖/轮椅） | ☆ 不可搭载，可联动 | 外挂传感器模块   | 通过蓝牙/低功耗模块传数据    |

**第二层：居家层（Home-Station）**

用户在家的固定交互点，承担深度对话和主动巡检。

| 设备类型                     | 搭载可行性   | 交互模态       | 典型场景                     |
| ---------------------------- | ------------ | -------------- | ---------------------------- |
| 自有语音终端（ADR-007）      | ★★★★★ 全功能 | 语音+屏幕+灯效 | 主动巡检、深度对话、安全守护 |
| 智能音箱/屏（小度/天猫精灵） | ★★★ 受限搭载 | 语音+屏幕      | 作为辅助入口（隐私降级场景） |
| 智能电视/机顶盒              | ★★★ 展示为主 | 大屏展示+语音  | 健康报告展示、用药提醒弹窗   |
| 平板电脑                     | ★★★★ 可搭载  | 触屏+语音      | 视频问诊、健康数据浏览       |

**第三层：联动层（Sensor & Link）**

不能或不需要搭载 Agent 的设备，但可以提供感知数据。

| 设备类型        | 联动方式            | 提供的数据                         |
| --------------- | ------------------- | ---------------------------------- |
| 血压计/血糖仪   | 蓝牙/Wi-Fi 数据同步 | 体征数据自动采集                   |
| 体重秤          | 蓝牙/Wi-Fi 数据同步 | 体重趋势追踪                       |
| 跌倒检测传感器  | Zigbee/BLE 报警     | 跌倒事件即时通知                   |
| 智能药盒        | BLE 用药记录        | 用药依从性数据                     |
| 门磁/人体传感器 | 智能家居网关        | 日常活动规律（是否起床、是否外出） |
| 拐杖外挂模块    | BLE 数据上报        | 使用频率、步态变化                 |
| 轮椅移动数据    | CAN/BLE 数据桥      | 活动范围、使用时长                 |

**Good, because...**

- 以用户已有设备为起点，降低接入门槛
- Agent 的"陪伴"覆盖用户全场景（在家 + 外出 + 移动中）
- 辅助设备成为 Agent 的"天然搭载点"——轮椅用户不需要额外买设备，轮椅本身就是 Agent
- 不适合搭载的设备也能提供关键数据（普通拐杖 → 加装传感器模块 → 步态数据）
- 设备故障时有冗余：手机坏了还有语音终端，语音终端坏了还有手表
- S9 核心引擎保持干净，设备适配不侵入决策逻辑
- 用户可以根据自己的偏好和条件自由组合设备

**Bad, because...**

- 多设备适配开发工作量大，需要分期实现
- 设备间的体验一致性难以保证（同一句话在手机上显示和在语音终端播报，效果不同）
- 设备发现、配对、切换的工程复杂度高
- 第三方设备（智能音箱、电视）的接入受平台限制
- 辅助设备接入涉及硬件改装，需要与辅具厂商合作或提供改装方案

### 方案 D：完全无硬件策略 — 纯软件

保持当前纯软件路线，通过 Web/App 提供文本+语音交互。

**Good, because...**

- 零硬件成本，零供应链风险
- 开发资源完全集中于软件

**Bad, because...**

- ADR-007 已充分论证"纯软件无法实现 C10 主动关怀和 C11 安全兜底的时效性"
- 否决

## Decision Outcome

**Chosen option: 方案 C — 设备生态策略**，核心引擎设备无关，多设备分层搭载、按需组合。


### 设备抽象层（DAL）设计原则

设备抽象层是连接 S9 与各类设备的关键中间层，负责：

1. **统一事件模型**：所有设备的输入统一为 `AgentEvent`（包含事件类型、来源设备、负载数据、优先级、时间戳）
2. **模态适配**：同一条 Agent 回复，根据目标设备的能力自动选择输出模态（有屏幕→显示文字+播放语音；只有扬声器→仅播放语音；只有屏幕→仅显示文字）
3. **设备路由**：根据消息优先级和用户当前活跃设备，决定消息发往哪个设备（紧急告警→所有设备同时推送；日常问候→仅在用户当前活跃设备上呈现）
4. **设备状态管理**：追踪每个设备的在线状态、电量、能力清单，Agent 据此调整交互策略

### 辅助设备的特殊设计

**原则：不适合搭载 Agent 的设备，通过"最小感知模块"实现联动。**

以普通手动轮椅为例：

- 用户不会为了一台智能轮椅而丢弃现有的手动轮椅
- 但可以加装一个小型蓝牙模块（成本 ¥30-50），包含：
  - 加速度计 → 检测移动/静止、活动时长
  - 陀螺仪 → 检测是否翻倒
  - 物理按钮 → 一键求助
- 模块通过 BLE 连接用户的手机，手机作为网关上传数据至 Haven
- Agent 感知到"轮椅 4 小时未移动"→ 触发主动巡检；"检测到翻倒加速度"→ 触发紧急告警

以普通拐杖为例：

- 在拐杖手柄处加装微型模块（成本 ¥20-30），包含：
  - 压力传感器 → 检测使用频率（是否在依赖拐杖行走）
  - 加速度计 → 步态分析（步态变化可能预示病情恶化）
  - 按钮 → 一键求助
- 数据通过 BLE 传至用户手机

**关键思路**：不是"做一个智能轮椅"，而是"让任何轮椅都能变成 Agent 的感知器官"。

### 用户设备画像

Agent 在用户画像（USER.md / S1 记忆系统）中维护用户的"设备画像"：

```yaml
device_profile:
  carry_layer: # 随身层
    - type: smartphone
      model: "iPhone 14"
      capabilities: [voice, screen, notification, ble_gateway]
      preference: primary # 用户首选交互设备
    - type: wheelchair
      model: "手动轮椅 + Haven 传感模块 v1"
      capabilities: [motion, fall_detect, sos_button]
      linkage: true # 不可搭载，仅联动
  home_layer: # 居家层
    - type: haven_terminal
      model: "Haven Voice Terminal v1"
      capabilities: [voice, screen, led, always_on]
  sensor_layer: # 联动层
    - type: blood_pressure_monitor
      model: "欧姆龙 BLE"
      capabilities: [bp_data]
    - type: smart_pillbox
      capabilities: [medication_log]
```

Agent 据此决定：

- 主动巡检时 → 优先通过居家层的语音终端（始终在线）
- 紧急告警时 → 所有随身层设备同时推送
- 日常提醒时 → 仅在用户当前活跃设备上通知
- 体征数据采集 → 从联动层的医疗设备自动同步

### 分期规划

| 阶段                    | 交付物                                                      | 依赖                  |
| ----------------------- | ----------------------------------------------------------- | --------------------- |
| Phase 1（设备无关核心） | S9 设备抽象层（DAL）+ 统一事件模型 + 手机 App 适配器（MVP） | S9 核心引擎稳定       |
| Phase 2（居家层）       | 自有语音终端适配器（ADR-007 Phase 1 终端 → 接入 DAL）       | ADR-007 原型验证完成  |
| Phase 3（联动层）       | 蓝牙医疗设备适配（血压计、血糖仪）+ 辅助设备传感模块原型    | 硬件模块选型与采购    |
| Phase 4（全覆盖）       | 辅助设备传感模块产品化 + 智能音箱/电视适配 + 多设备智能路由 | 供应链 + 辅具厂商合作 |

### 与 ADR-007 的关系

本 ADR **不是**推翻 ADR-007，而是**扩展**其视野：

| 维度     | ADR-007 的视角           | ADR-009 的扩展                   |
| -------- | ------------------------ | -------------------------------- |
| 设备范围 | 自建语音终端             | 用户生活中的所有设备             |
| 搭载逻辑 | Agent = 一台具体设备     | Agent = 跨设备的连续体验         |
| 辅助设备 | 未涉及                   | 核心关注对象，区分"搭载"与"联动" |
| 手机定位 | "辅助入口，不纳入本 ADR" | 随身层核心设备，优先适配         |
| 用户选择 | 默认使用自建终端         | 用户偏好驱动，自由组合           |

ADR-007 的自建语音终端仍然是居家层的核心设备——它的"始终在线"和"主动巡检"能力是其他消费级设备无法替代的。但用户**不必**先买语音终端才能用 Haven：他们可以从手机开始，逐步添加设备。

## Consequences

**Good:**

- **零门槛起步**：用户不需要购买任何新硬件即可开始使用 Haven（通过手机 App/小程序），降低获客阻力
- **陪伴不中断**：Agent 在用户移动时（出门、看病）通过手机/手表继续保持连接，而非"出门就失联"
- **辅助设备赋能**：轮椅、拐杖等辅助设备从"沉默的工具"升级为 Agent 的感知器官——这是竞争对手难以复制的差异化能力
- **用户选择自由**：技术爱好者可以组装全套设备，节俭的用户可以只用手机，轮椅用户可以依赖轮椅上的传感模块——Agent 适应人，而非人适应 Agent
- **设备冗余**：多设备互为备份，单点故障不会导致 Agent 失联
- **渐进式交付**：设备层分期建设，不影响 S9 核心引擎的独立演进
- **核心引擎干净**：S9 的决策逻辑与设备形态完全解耦，未来出现新形态设备（如 AR 眼镜）时无需改动核心

**Bad:**

- **多设备适配的开发成本**：每类设备都需要一个适配器，初期工程量大；需优先实现手机 + 自有终端，其余按需扩展
- **体验一致性挑战**：同一句话在手机屏幕上显示文字 vs 在语音终端播报语音，用户体验有差异；需要通过模态适配引擎尽量统一
- **辅助设备改装的用户接受度**：在轮椅/拐杖上加装模块需要用户接受"设备改造"，部分用户可能有抵触；需要设计无感安装方案
- **第三方平台依赖**：智能音箱、电视等接入受平台方 API 限制，可能随时变更；优先发展自有设备，第三方作为补充
- **设备发现的工程复杂度**：多设备间的发现、配对、状态同步、消息路由需要可靠的分布式协议，工程复杂度高于单一设备方案
- **安全攻击面扩大**：每增加一个设备就增加一个攻击入口，需要统一的设备认证和安全策略

**Neutral:**

- 本 ADR 不改变 S9 Agent 核心引擎的架构和演进路线，仅在其外围增加设备抽象层
- 设备适配器按需开发，不强制所有设备同时实现
- 辅助设备的"最小感知模块"需要独立的硬件研发线，与软件迭代并行推进
- 本 ADR 不承诺具体实现时间表，仅确立"设备生态"的战略方向

---

> **一句话总结**：Haven 不应该只是一台设备，而应该是一个"能跟着用户走"的陪伴——用户在哪，Agent 就在哪。智能体搭载在哪不重要，重要的是它懂用户的设备偏好、尊重用户的生活习惯、并能在用户最依赖的那些东西（手机、手表、轮椅、拐杖）上找到自己的位置。能搭载就搭载，不能搭载就联动——Agent 的触角比 Agent 的身体更重要。
