# ADR-007：语音交互与实体部署 — 从软件智能体走向"陪伴在身边"

- **Status**: Proposed (2026-09-29)
- **Deciders**: Haven 项目组
- **Date**: 2026-09-29
- **Depends on**: ADR-001, ADR-002, ADR-003, ADR-005, ADR-006

## Context

Haven 当前定位为"个人慢病管理智能体"（ADR-001），核心交互形式为文本对话（通过 CLI / Web Chat / LangGraph Studio）。然而，目标用户群体（40-70 岁慢病患者）中存在一个显著的接入障碍：

- **文字输入门槛**：老年慢病患者中相当比例不熟悉键盘输入，或受视力、手部灵活性限制，文字交互体验差；
- **"在场感"缺失**：当前 Haven 运行在开发机或服务器上，用户须主动打开终端/浏览器才能对话——这与 ADR-002 定义的"C10 主动关怀"能力之间存在**物理鸿沟**：Agent 想主动问候用户，但没有一个"能说话、能听到"的物理载体；
- **安全守护的时效性**：C11 安全兜底要求 Agent 能在关键时刻识别并干预，但如果用户无法及时打开设备，安全守护形同虚设。一个始终在线的实体设备可以**定期主动询问用户状况**，在无响应时触发升级通知。

因此，Haven 需要一条明确的技术路线图，从纯软件的文本对话智能体，走向具备**语音交互能力、可部署到外部实体机器、支持唤醒和主动安全巡检**的"陪伴在身边"的智能体。

## Decision Drivers

- **降低交互门槛**：让不擅长打字的老年慢病患者也能自然使用，语音是最直观的交互方式
- **实现主动关怀的物理基础**：Agent 的"主动问候、定期查看、安全确认"需要一个始终在线、能发出声音的物理载体
- **隐私与数据安全**：健康数据不得经过不可控的第三方语音平台
- **部署形态**：需要从软件方案走向软硬一体，明确硬件选型与部署策略
- **唤醒机制**：支持语音唤醒词，降低交互摩擦
- **渐进式交付**：不改变当前 0.0.1 的交付节奏，语音+实体作为远期里程碑

## Considered Options

### 方案 A：对接第三方智能音箱平台（如小度、天猫精灵 Alexa Skill）

通过开发第三方智能音箱的 Skill/Action 接入 Haven API，借助现有音箱设备实现语音交互。

**Good, because...**

- 设备普及率高，用户可能已有智能音箱
- 语音识别（ASR）和合成（TTS）由平台提供，开发成本低

**Bad, because...**

- 健康数据必须经过第三方云平台，隐私合规风险极大
- 唤醒词由平台控制，无法自定义（如"小Haven"或用户自定义名称）
- 平台 SDK 限制多，主动推送/定时巡检能力受限——C10 主动关怀难以实现
- 依赖外部平台生态，随时面临 API 变更或商业化限制
- **否决**

### 方案 B：纯手机 App 语音交互

开发移动端 App，利用手机麦克风和扬声器实现语音对话，通过 App 后台保活实现主动推送。

**Good, because...**

- 智能手机已普及，不需要额外硬件成本
- 可完全控制数据链路，隐私有保障
- 支持推送通知实现部分主动关怀

**Bad, because...**

- "始终在线"依赖 App 后台保活，iOS/Android 均有严格的省电限制，无法保证长期稳定运行
- 手机不是"环境设备"——用户需要找到手机、解锁、打开 App 才能交互，丧失"唤醒即聊"的便捷性
- 40-70 岁用户群体中，仍有相当比例不熟悉智能手机操作
- 安全巡检需要 App 持续运行，移动端难以做到真正的"定时主动查看"
- **保留作为辅助入口，但不作为主方案**

### 方案 C：自建软硬一体方案（采纳）

基于嵌入式 Linux 单板计算机（如树莓派 / Orange Pi）或专用智能屏设备，自研语音交互终端。终端部署到用户家中，通过 Wi-Fi 连接 Haven 云端服务，本地完成唤醒词检测和语音采集，云端完成 ASR / LLM 推理 / TTS。

**Good, because...**

- 完整的隐私控制：音频数据可端到端加密，唤醒词检测本地完成，健康数据不经过第三方
- 真正的"始终在线"：插电常驻，不依赖电池和省电策略
- 完美支持 C10 主动关怀：Agent 可定时发言、主动询问、在无响应时升级通知
- 唤醒词可自定义：可设计为"小Haven"或用户偏好的名称
- 硬件成本可控：树莓派级别的单板计算机成本在 ¥200-500 区间
- 可设计适老化外观：大按钮、大字体屏幕、简洁指示灯，降低使用门槛

**Bad, because...**

- 需要硬件供应链：采购、组装、物流、售后——这是软件团队不熟悉的领域
- 部署运维复杂：设备配网、固件更新、故障恢复都需要远程运维能力
- 家庭网络环境的多样性：Wi-Fi 信号差、NAT 穿透、断网降级需要逐案处理
- 总交付周期长，不适合在 0.0.1 阶段引入

### 方案 D：混合方案 — 实体终端为主，手机 App 辅助

在方案 C 的基础上，同时提供轻量手机 App 作为辅助入口（如家属远程查看、紧急通知），但主交互载体为实体语音终端。

**Good, because...**

- 覆盖面最广：家中用终端，外出用手机
- 家属可通过 App 远程查看安全状态

**Bad, because...**

- 开发复杂度最高
- 与方案 C 面临相同的硬件挑战

## Decision Outcome

**Chosen option: 方案 C — 自建软硬一体语音交互终端**，作为 Haven 从纯软件走向"陪伴在身边"的长期方向。

手机 App（方案 B）作为远期辅助入口保留，但不在本 ADR 范围内决策。

### 语音交互流程

```
用户说"小Haven" → 本地唤醒词检测触发
  → 终端播放"叮"提示音，开始收音
  → 用户说话 → 音频流送云端 ASR → 转文字
  → 文字输入 S9 Agent 决策循环 → 生成回复文本
  → 回复文本送 TTS → 语音流回终端播放
  → 终端恢复待唤醒状态

主动巡检（后台定时触发）：
  → S5 通信系统按配置间隔（如每 4 小时）触发巡检任务
  → Agent 生成问候/询问语句（如"您今天感觉怎么样？血压测了吗？"）
  → TTS 合成 → 推送至终端播放
  → 等待用户响应
  → 若超时无响应，升级通知家属/紧急联系人
```

| OTA 更新   | Mender / RAUC                      | 远程固件升级，保障终端持续迭代                   |

### 主动安全巡检机制

这是本 ADR 区别于"一个能说话的音箱"的核心设计——Agent 不是被动等待唤醒，而是**主动定期查看用户**：

1. **定时巡检**：S5 通信系统按可配置间隔（默认每 4 小时，夜间静默）发起巡检
2. **轻量询问**：Agent 生成简短问候（如"您还好吗？"），TTS 后通过终端播放
3. **响应判断**：
   - 用户语音响应 → Agent 进入正常对话
   - 用户按终端上的物理按钮 → 确认安全
   - 超时无响应（如连续 2 次巡检无应答）→ **升级**
4. **升级链路**：终端本地声光报警 → 推送通知至家属 App/短信 → 紧急情况拨打预设电话
5. **降级策略**：若 Wi-Fi 断开，终端本地缓存巡检记录，恢复连接后同步

### 分期规划

| 阶段                | 交付物                                                              | 依赖              |
| ------------------- | ------------------------------------------------------------------- | ----------------- |
| Phase 1（原型验证） | 树莓派 + 麦克风阵列 + 唤醒词 + ASR/TTS 云端服务 → 基础语音对话 Demo | 当前 0.0.1 完成后 |
| Phase 2（主动巡检） | 定时巡检调度 + 无响应升级链路                                       | S5 通信系统建设   |
| Phase 3（产品化）   | 工业设计外壳 + OTA 更新 + 配网流程 + 适老化 UX（大按钮、指示灯）    | 硬件供应链        |
| Phase 4（生态扩展） | 家属 App、可选传感器扩展（跌倒检测、环境监测）                      | 手机 App 开发     |

## Consequences

**Good:**

- 真正实现 ADR-001 的"长期陪伴"愿景：从"工具"走向"伙伴"
- C10 主动关怀从 PASSIVE（等待用户打开）变为 ACTIVE（始终在场、主动问候）
- C11 安全兜底的时效性大幅提升——Agent 可以在用户无法操作设备时主动发现异常
- 语音交互将 Haven 的可达人群从"会用手机/电脑的慢病患者"扩展到"几乎所有慢病患者"
- 软硬一体的方案确保隐私数据全程可控，符合医疗健康领域的数据合规要求

**Bad:**

- 硬件供应链和运维是全新领域，团队需要补充硬件工程、工业设计、供应链管理能力或寻找合作伙伴
- 家庭网络环境复杂：NAT 穿透、弱网降级、配网失败等场景需要逐案处理
- 终端安全攻击面增大：物理设备可能被篡改，固件签名和 Secure Boot 需要纳入设计
- 售后运维成本：设备故障、用户不会操作等需要建立客服和远程诊断体系
- 交付周期长：从原型到量产至少需要 12-18 个月，不适合作为短期目标

**Neutral:**

- 不影响当前 0.0.1 的文本对话交付路线，Agent 核心引擎（S9）的决策逻辑与输入模态解耦，语音交互只是**新增一种输入/输出通道**
- ASR/TTS 服务虽然新增，但遵循 S3（数据采集）和 S5（通信系统）的架构边界，不侵入 Agent 核心
- 本 ADR 不承诺实现时间表，仅确立技术方向，供后续版本规划参考

---

> **一句话总结**：Haven 的长期愿景是从屏幕后走到用户身边——通过一个始终在线的语音终端，让慢病老人只需开口说话就能获得陪伴与守护，而 Agent 也会主动、定期查看他们是否安好。
