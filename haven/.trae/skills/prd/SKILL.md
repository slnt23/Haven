# PRD（产品需求文档）格式规范

需求文档的核心目标是**对齐交付**：让开发知道怎么做、测试知道怎么验、业务知道怎么衡量效果。

与 ADR 记录"架构决策"不同，PRD 是**活文档**，允许迭代更新，但每次修改必须在变更记录中留痕。

## 一份合格 PRD 必须回答的四个问题

### 1. 为什么做？（背景与目标）

用**数据**说话，而不是主观感受。同时明确**成功指标**（可量化）和**非目标**（本期明确不做什么），防止范围蔓延。

```markdown
## 背景与目标

### 问题证据

上季度流失率从 8% 升至 12%，调研中"设置复杂"的反馈上升 40%。

### 业务目标

通过简化设置流程，将流失率拉回 8% 以下。

### 成功指标

- 设置流程完成率 ≥ 85%（当前 62%）
- 设置平均耗时 ≤ 2 分钟（当前 4.5 分钟）

### 非目标（本期不做）

- 不重构整体信息架构
- 不新增第三方登录方式
```

### 2. 为谁做？（用户与场景）

用**用户故事**格式统一语言：`作为[角色]，我希望[功能]，以便[价值]`。场景描述覆盖**触发条件 → 用户操作 → 预期结果**。

```markdown
## 用户与场景

### 目标角色

- 新注册用户（首次登录，未设置任何资料）

### 主路径

新用户登录后 → 看到设置引导卡片 → 3 步内完成昵称、头像、感兴趣领域 → 进入首页

### 高频异常场景

- 用户跳过设置：下次登录再次引导，但允许"暂不设置"
- 网络中断：已填内容本地暂存，恢复后自动回填
```

### 3. 做什么？（功能详述）

核心在于**可判定**：规则要能让开发确定"什么条件下执行什么动作"，让测试能构造用例。必须覆盖三类流程：

- **正常路径**：理想情况下的完整操作流
- **异常路径**：网络中断、数据非法、权限不足
- **边界条件**：列表为空、达到上限、极端值

```markdown
## 功能详述

### 用户故事

作为新用户，我希望在登录后 3 步内完成资料设置，以便快速开始使用产品。

### 业务规则

- 昵称：2-20 字符，不含特殊符号，实时校验
- 头像：支持拍照/相册，裁剪为 1:1，≤ 5MB
- 跳过时：本次不展示但记录"已跳过"，7 天后再提醒

### 异常处理

| 异常     | 处理                                       |
| -------- | ------------------------------------------ |
| 昵称违规 | 输入框标红，提示具体违规原因               |
| 网络中断 | 提示"网络异常，已保存草稿"，恢复后自动回填 |
| 头像过大 | 上传前客户端压缩，超过 10MB 则拒绝并提示   |
```

### 4. 怎么算做完了？（验收标准）

写成**可观察的结果**，推荐 Given-When-Then 格式。写文档时就把验收条件定下来，不要等测试阶段再补。

```markdown
## 验收标准

### AC-1: 正常完成设置

**Given** 新用户首次登录，进入设置引导
**When** 填写合法昵称、上传头像、点击"完成"
**Then** 跳转首页，顶部显示昵称和头像，设置引导不再出现

### AC-2: 跳过设置

**Given** 新用户在设置引导第 1 步
**When** 点击"暂不设置"
**Then** 进入首页，引导卡片消失，7 天后再次展示

### AC-3: 昵称非法

**Given** 新用户在昵称输入页
**When** 输入单个字符"a"
**Then** 输入框标红，提示"昵称至少 2 个字符"，"完成"按钮置灰
```

## PRD 完整骨架

生成 PRD 时使用以下结构，根据实际需求增减章节：

```markdown
# PRD-{编号}: {需求标题}

## 文档信息

| 字段     | 值                                                                                         |
| -------- | ------------------------------------------------------------------------------------------ |
| 版本     | v1.0                                                                                       |
| 作者     | @xxx                                                                                       |
| 日期     | YYYY-MM-DD                                                                                 |
| 状态     | Draft / Review / Approved                                                                  |
| 关联文档 | {经检索后列出所有相关的 REQ/ADR/SPRINT 编号、标题及关联说明；如无则标注"无（经检索确认）"} |

## 背景与目标

- 问题证据（数据支撑）
- 业务目标（可量化）
- 成功指标（明确数字）
- 非目标（本期明确不做）

## 范围

- **Must**：本期必须交付
- **Should**：本期尽量交付
- **Not now**：明确不做，列入后续版本

## 用户与场景

- 目标角色
- 主路径（触发条件 → 操作 → 预期结果）
- 高频异常场景

## 功能详述

- 用户故事
- 业务规则（可判定）
- 正常流程、异常流程、边界条件
- 交互说明 / 原型图引用

## 非功能需求

- 性能指标
- 安全与隐私
- 兼容性要求
- 埋点与数据

## 验收标准

- Given-When-Then 格式
- 可测试、可追溯

## 附录

- 原型图 / 流程图链接
- 名词解释
- 变更记录（每次修改留痕：改了什么、为什么改、影响哪些模块）
```

## 与 ADR 的关键区别

|          | ADR                        | PRD                                      |
| -------- | -------------------------- | ---------------------------------------- |
| 记录内容 | 架构决策与权衡             | 产品功能与交付标准                       |
| 目标读者 | 架构师、Tech Lead          | 开发、测试、设计、业务                   |
| 变更管理 | **不可修改**，只能新增取代 | **活文档**，允许迭代，但变更记录必须留痕 |
| 核心要求 | 写下负面后果               | 覆盖异常路径与边界条件                   |

## 创建前：检索已有文档，建立关联

在创建新的 PRD 之前，**必须先检索已有需求文档和 ADR**，确认是否存在与该需求主题相关的既往记录。

### 检索范围

1. **需求文档目录**（`docs/requirements/`）：检索所有 REQ-XXX、SPRINT-XXX 等需求文档
2. **ADR 目录**（`docs/adr/`）：检索与该需求相关的架构决策记录
3. 相关性的判断标准：
   - 同一用户故事或功能的延续/细化（如都是关于健康画像、用药管理）
   - 同一系统模块或技术组件（如都是关于通信系统、记忆系统）
   - 同一产品方向或用户场景（如都是关于语音交互、主动关怀）
4. 无关旧文档不需要引用

### 如果找到相关联的旧文档，必须：

1. **在文档信息的"关联文档"字段中详细声明**：列出所有相关文档的编号、标题，并简要说明关联关系（本需求是对旧需求的扩展/细化/替代/依赖）
2. **在背景段落中说明关联**：明确描述本需求与旧记录的承接关系
3. **在范围段落中区分新旧**：如果旧需求中有已实现/未实现的相关功能，在本需求的范围说明中明确标注——哪些是新功能、哪些是对旧功能的增强、哪些旧功能保持不变

### 关联声明示例

```markdown
| 关联文档                                                                    |
| --------------------------------------------------------------------------- |
| REQ-001 F1 健康画像管理：本需求是在 F1 基础上的"语音输入画像"扩展（扩展）   |
| ADR-007 语音交互与实体部署：本需求是 ADR-007 语音终端的具体功能需求（依赖） |
| SPRINT-0.0.1：本需求不影响 0.0.1 范围，列为后续 sprint（无冲突）            |
```

### 关联类型说明

| 关联类型              | 场景                             | 背景段落写法示例                                                         |
| --------------------- | -------------------------------- | ------------------------------------------------------------------------ |
| 扩展（extends）       | 新需求是在旧需求基础上的新增功能 | "REQ-001 已定义健康画像的文本录入方式，本需求在此基础上新增语音录入通道" |
| 细化（refines）       | 新需求是对旧需求的进一步细化     | "SPRINT-0.0.1 中健康画像仅支持表单录入，本需求细化其 NL 解析交互"        |
| 依赖（depends）       | 新需求依赖旧需求或 ADR 的决策    | "本需求依赖 ADR-007 中确定的语音终端硬件方案"                            |
| 替代（supersedes）    | 新需求取代旧需求                 | "REQ-003 中「仅文本交互」的限制被本需求推翻，代之以多模态交互"           |
| 无冲突（independent） | 相关但互不影响                   | "与 SPRINT-0.0.1 无功能重叠，独立交付"                                   |

### 如果检索后确认无相关旧文档

在 PRD 中明确标注：

```markdown
| 关联文档 | 无（经检索，无与本需求主题相关的既往需求文档或 ADR） |
```

## 常见错误

1. **只写正常流程**：新手 PRD 最常见的通病。每条用户故事都必须同时描述异常处理和边界条件。
2. **验收标准不可判定**："功能正常可用"无法测试。必须写成"提交后列表中出现该记录且状态为'待审核'"这样的可观察结果。
3. **不写非目标**：没有 Non-goals 就容易被 stakeholder 不断追加需求，导致范围蔓延。
